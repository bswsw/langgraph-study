CHAPTER 13

계층적 에이전트 팀

감독자 한 명이 모든 작업자를 직접 지휘하는 구조는 작업이 단순하고 작업자가 적을 때만 잘 동작한다. 하위 영역이 늘고 작업자가 많아지면 감독자 한 명이 모든 지시와 판단을 맡기 어렵고, LLM의 컨텍스트 윈도우 한계에도 부딪힌다. 계층적 에이전트 팀(Hierarchical Agent Team)은 상위 감독자가 하위 감독자에게 일을 나눠 주고, 하위 감독자가 자기 영역의 작업자를 관리하는 다단계 구조로 이 문제를 푼다.

★ 핵심 — 왜 계층이 필요한가

작업 복잡도 증가와 작업자 수 증가가 함께 오면 감독자 한 명으로는 감당이 안 된다. 감독자 한 명이 모든 작업자에게 직접 지시하면 관리 부담이 커지고 컨텍스트 윈도우 한계에 부딪힌다. 그래서 "웹 연구"와 "문서 작성"처럼 성격이 다른 일을 각 전문 팀이 맡도록 나눈다.

이 장의 예제는 AutoGen 논문(arXiv 2308.08155)의 아이디어를 LangGraph로 구현한 것이다. 웹 연구(Research)와 문서 작성(Doc Writing)을 서로 다른 팀으로 만들고, 상위 감독자와 팀 감독자가 전체 흐름을 관리한다.

01. 도구 생성하기

각 팀의 작업자는 하나 이상의 도구를 가진다. 팀별로 필요한 도구를 먼저 모두 정의한다.

Research Team 도구

도구역할구현
TavilySearch웹 검색 (최대 5개 결과)TavilySearch(max_results=5)
scrape_webpagesURL 목록의 본문 스크래핑@tool + WebBaseLoader
pythonscrape_webpages — 결과를 XML 형식으로 반환
@tool
def scrape_webpages(urls: List[str]) -> str:
    """웹 페이지 스크래핑 도구"""
    loader = WebBaseLoader(
        web_path=urls,
        header_template={"User-Agent": "Mozilla/5.0 ..."},  # 봇 차단 방지
    )
    docs = loader.load()
    return "\n\n".join([
        f'<Document name="{doc.metadata.get("title", "")}">\n{doc.page_content}\n</Document>'
        for doc in docs
    ])

User-Agent 헤더는 봇 차단을 피하기 위한 것이다. 결과를 XML 태그로 감싸서 LLM이 문서의 경계와 제목을 구조적으로 이해하기 쉽게 만든다.

02. 유틸리티 함수 정의하기

AgentFactory — 팩토리 패턴

LLM은 한 번만 초기화하고 같은 설정으로 여러 에이전트를 만들기 위한 클래스다. 핵심은 에이전트를 그래프 노드 함수로 바꿔 주는 create_agent_node다.

python★ 결과를 이름 붙인 HumanMessage로 변환
class AgentFactory:
    def __init__(self, model_name):
        self.llm = init_chat_model(model_name, temperature=0)

    def create_agent_node(self, agent, name: str):
        def agent_node(state):
            result = agent.invoke(state)
            return {"messages": [
                HumanMessage(content=result["messages"][-1].content, name=name)
            ]}
        return agent_node

agent_factory = AgentFactory("claude-sonnet-4-5")
search_agent = create_agent(llm, tools=[tavily_tool])
search_node = agent_factory.create_agent_node(search_agent, name="Searcher")
★ 핵심 — 왜 HumanMessage로 감싸는가

감독자가 모든 작업자의 결과를 같은 메시지 형식으로 받아야 다음 결정을 일관되게 내릴 수 있다. name 매개변수로 어떤 에이전트가 만든 결과인지 구분한다. 에이전트 내부의 도구 호출 과정은 버리고 마지막 메시지만 감독자에게 전달한다는 점도 중요하다.

팀 감독자 생성 함수 — create_team_supervisor

멤버 중 다음 작업자를 고르거나, 일이 끝나면 FINISH를 반환하는 감독자 체인을 만든다. 계층적 시스템의 모든 감독자(팀 감독자 2개, 총 감독자 1개)가 이 함수 하나로 만들어진다.

python★ 구조화된 출력으로 라우팅 선택지를 강제
def create_team_supervisor(model_name, system_prompt, members):
    options_for_next = ["FINISH"] + members

    class RouteResponse(BaseModel):
        next: Literal[*options_for_next]   # 멤버 이름 또는 FINISH만 허용

    prompt = ChatPromptTemplate.from_messages([
        ("system", system_prompt),
        MessagesPlaceholder(variable_name="messages"),
        ("human",
         "Given the conversation above, who should act next? "
         "Or should we FINISH? If the requested tasks have been completed, "
         "you MUST select FINISH. Do NOT repeat completed tasks. "
         "Select one of: {options}"),
    ]).partial(options=str(options_for_next))

    llm = init_chat_model(model_name, temperature=0)
    return prompt | llm.with_structured_output(RouteResponse)
  • Literal[*options_for_next]: 멤버가 ["Searcher", "WebScraper"]이면 LLM은 "FINISH", "Searcher", "WebScraper" 중 하나만 고를 수 있다. 잘못된 라우팅을 막는다.
  • 라우팅 지시를 마지막 human 메시지로 넣는 이유: Claude 모델은 system 메시지가 맨 앞에 연속으로 있어야 하기 때문이다.
  • "Do NOT repeat completed tasks", "you MUST select FINISH"처럼 반복 방지 지시를 프롬프트에 명시한다.

팀 상태 ResearchState는 messages(add_messages 리듀서), team_members, next 세 필드로 구성된다. Searcher와 WebScraper 노드를 만들고, 팀 감독자에 두 멤버를 등록한다.

def get_next_node(x):
    return x["next"]                       # 감독자가 고른 next 값을 그대로 반환

web_research_graph = StateGraph(ResearchState)
web_research_graph.add_node("Searcher", search_node)

실행 도우미 run_graph

RunnableConfig(recursion_limit=..., configurable={"thread_id": random_uuid()})로 설정한 뒤 invoke_graph로 실행하고 app.get_state(config).values를 반환한다. 예제에서는 네이버 금융 뉴스 URL을 주고 주요 뉴스를 정리하도록 요청한다.

★ 핵심 — recursion_limit

recursion_limit은 그래프가 무한 루프에 빠지지 않게 하는 안전장치다. 계층적 시스템은 여러 단계의 노드를 거치므로 충분히 큰 값을 설정해야 한다. 대부분은 기본값 50이면 충분하다. 또 계층적 감독자 체인은 stream_mode="messages"와 호환되지 않아서 invoke_graph를 쓴다.

상태 DocWritingState에는 Research 팀 필드 외에 current_files(작업 디렉터리 파일 목록)가 추가된다.

python★ preprocess | agent — 실행 전에 파일 목록 주입
def preprocess(state):
    written_files = [f.relative_to(WORKING_DIRECTORY)
                     for f in WORKING_DIRECTORY.rglob("*")]
    if not written_files:
        return {**state, "current_files": "No files written."}
    return {**state, "current_files":
        "\nBelow are files your team has written to the directory:\n"
        + "\n".join([f" - {f}" for f in written_files])}

doc_writer_agent = create_agent(llm,
    tools=[write_document, edit_document, read_document],
    system_prompt="You are a arxiv researcher. ...")
context_aware_doc_writer_agent = preprocess | doc_writer_agent
doc_writing_node = agent_factory.create_agent_node(
    context_aware_doc_writer_agent, name="DocWriter")
★ 핵심 — 파일을 통한 작업자 간 협업

파이프 연산자로 preprocess | agent를 결합하면 에이전트 실행 직전에 파일 목록이 자동으로 갱신된다. 덕분에 DocWriter가 NoteTaker가 만든 아웃라인 파일을 인식하고 참조할 수 있다. 메시지만이 아니라 파일 시스템을 공유 작업 공간으로 쓰는 방식이다.

Doc Writing 감독자의 시스템 프롬프트에는 작업 순서를 직접 적어 무한 루프를 막는다.

prompt워크플로 순서 명시
WORKFLOW: NoteTaker(outline) -> DocWriter(content) -> ChartGenerator(if needed)
          -> DocWriter(save) -> FINISH.
Once the document is saved, respond with FINISH immediately.
Do NOT repeat any step that has already been completed.

그래프는 Research Team과 같은 구조다(작업자 3개 → Supervisor, Supervisor → 조건부 에지). 예제는 "Transformer 구조에 대한 논문 목차 작성 → 각 목차 5문장 이상 → 필요 시 차트 → 저장"을 요청한다.

04. 슈퍼그래프 생성하기

이 설계는 상향식 계획 정책(Bottom-up Planning Policy)을 따른다. 하위 팀 그래프를 먼저 만들고, 그 위에 두 팀을 조정하는 슈퍼그래프(Super-Graph)를 얹는다. 슈퍼그래프가 맡는 일은 세 가지다.

팀 간 작업 라우팅

요청에 맞는 팀에 작업 할당

상태 공유 관리

서로 다른 그래프 사이의 상태 공유 방식 정의

최종 결과 조합

각 팀 결과를 모아 최종 응답 생성

총 감독자 노드

같은 create_team_supervisor에 멤버만 ["ResearchTeam", "PaperWritingTeam"]으로 바꿔 만든다.

prompt★ 총 감독자 프롬프트의 반복 방지 지시
IMPORTANT: Assign each team at most once. Once a team has reported
its results, do NOT assign it again. When all teams have completed
their tasks, respond with FINISH immediately.
★ 핵심 — 프롬프트로 무한 루프 방지

계층적 시스템에서는 팀 간 반복 호출로 무한 루프가 생길 위험이 있다. 그래서 "각 팀은 최대 한 번만 할당"이라는 규칙을 프롬프트에 명시한다. 이 장에서는 루프 방지가 세 겹으로 나타난다. ① 팀 감독자의 "Do NOT repeat", ② Doc 팀의 WORKFLOW 순서, ③ 총 감독자의 "at most once", 그리고 마지막 안전장치로 recursion_limit이 있다.

상태 변환 함수 — get_last_message / join_graph

슈퍼그래프 상태 State는 messages와 next만 가진다. 하위 팀의 ResearchState / DocWritingState와 필드가 다르므로 변환 함수가 반드시 필요하다.

python★ 서로 다른 상태 스키마를 잇는 어댑터
def get_last_message(state: State) -> str:
    # 슈퍼그래프 → 팀: 전체 히스토리 중 마지막 메시지만 전달
    last_message = state["messages"][-1]
    if isinstance(last_message, str):
        return {"messages": [HumanMessage(content=last_message)]}
    return {"messages": [last_message.content]}

def join_graph(response: dict):
    # 팀 → 슈퍼그래프: 팀 실행 결과 중 마지막 메시지만 반영
    return {"messages": [response["messages"][-1]]}

super_graph = StateGraph(State)
super_graph.add_node("ResearchTeam",
    get_last_message | web_research_app | join_graph)
super_graph.add_node("PaperWritingTeam",
    get_last_message | authoring_app | join_graph)
super_graph.add_node("Supervisor", supervisor_node)

super_graph.add_edge("ResearchTeam", "Supervisor")
super_graph.add_edge("PaperWritingTeam", "Supervisor")
super_graph.add_conditional_edges("Supervisor", get_next_node,
    {"PaperWritingTeam": "PaperWritingTeam",
     "ResearchTeam": "ResearchTeam", "FINISH": END})
super_graph.set_entry_point("Supervisor")
super_graph = super_graph.compile(checkpointer=MemorySaver())
★ 핵심 — 컴파일된 팀 그래프 = 하나의 노드

컴파일된 서브그래프(web_research_app)도 Runnable이므로 입력 변환 | 서브그래프 | 출력 변환 파이프라인으로 감싸 상위 그래프의 노드 하나로 넣을 수 있다. 마지막 메시지만 주고받기 때문에 팀 내부의 긴 대화가 상위로 새지 않아 컨텍스트가 간결하게 유지된다. 계층 구조가 컨텍스트 한계를 푸는 핵심 메커니즘이다.

실행

"multi-agent 구조로 복잡한 작업을 수행하는 방법"을 주제로 arXiv 형식 리포트(아웃라인, 각 5문장 이상, 필요 시 차트, 한글, APA 인용, .md 저장)를 요청한다. 총 감독자가 먼저 ResearchTeam에 연구를 맡기고, 그 결과로 PaperWritingTeam이 문서를 작성하는 전체 과정이 자동으로 진행된다. 결과는 IPython.display.Markdown으로 렌더링해 확인한다.

LangGraph를 활용하여 에이전트 구축하기

질문의 성격에 따라 직접 답하거나 필요한 도구를 호출하는 에이전트를 만든다. "대한민국의 수도는?"에는 LLM이 바로 답하고, "오늘 날씨는?"처럼 최신 정보가 필요하면 웹 검색 도구를 호출한 뒤 답한다. 고정된 대화 흐름이 아니라 상황에 따라 달라지는 실행 흐름을 그래프로 명시하는 것이 핵심이다.

★ 핵심 — 세 가지 구성 요소의 역할
  • 모델 노드(chatbot): 사용자 질문을 해석하고 답하거나 도구 호출을 생성
  • 도구 노드(tools): 필요한 외부 정보를 실제로 가져옴
  • 조건부 에지: 응답에 tool_calls가 있으면 도구로, 없으면 종료

이 구조 덕분에 질문마다 같은 경로를 밟는 챗봇이 아니라 도구 사용 여부에 따라 동적으로 동작하는 에이전트가 된다.

01. 도구 사용하기 — 상태 · LLM 바인딩 · 노드

python상태 정의
class State(TypedDict):
    messages: Annotated[list, add_messages]   # 덮어쓰지 않고 자동 추가
python★ bind_tools — 도구 바인딩
tool = TavilySearch(max_results=3)
tools = [tool]

llm = init_chat_model("claude-sonnet-4-5")
llm_with_tools = llm.bind_tools(tools)

def chatbot(state: State):
    answer = llm_with_tools.invoke(state["messages"])
    return {"messages": [answer]}             # add_messages가 기존 목록에 추가

graph_builder = StateGraph(State)
graph_builder.add_node("chatbot", chatbot)
★ 핵심 — bind_tools는 실행하지 않는다

bind_tools()는 LLM에게 사용 가능한 도구 목록을 알려 줄 뿐이다. LLM은 필요할 때 도구를 고르고 호출 인자를 만들지만, 실제 도구 실행은 일어나지 않고 도구 호출 요청(tool_calls)만 생성된다. 실행은 별도의 도구 노드가 맡는다.

02. BasicToolNode 구현하기

도구 노드는 LLM이 만든 도구 호출 요청을 실제로 실행한다. 마지막 AIMessage의 tool_calls를 순서대로 실행하고 결과를 ToolMessage로 반환한다.

python★ 도구 노드의 내부 동작
class BasicToolNode:
    def __init__(self, tools: list) -> None:
        self.tools_list = {tool.name: tool for tool in tools}   # 이름 → 도구

    def __call__(self, inputs: dict):
        if messages := inputs.get("messages", []):
            message = messages[-1]
        else:
            raise ValueError("No message found in input")

        outputs = []
        for tool_call in message.tool_calls:
            tool_result = self.tools_list[tool_call["name"]].invoke(tool_call["args"])
            outputs.append(ToolMessage(
                content=json.dumps(tool_result, ensure_ascii=False),
                name=tool_call["name"],
                tool_call_id=tool_call["id"],     # 어떤 호출의 결과인지 매칭
            ))
        return {"messages": outputs}

tool_node = BasicToolNode(tools=[tool])
graph_builder.add_node("tools", tool_node)

각 ToolMessage에는 도구 이름과 호출 ID가 들어 있어서, LLM이 어떤 도구 호출에 대한 결과인지 정확히 매칭할 수 있다.

직접 구현은 내부 동작을 이해하는 데 유용하다. 실제 프로덕션에서는 LangGraph의 ToolNode를 쓰면 오류 처리, 병렬 실행 등을 기본으로 제공받을 수 있어 더 편리하다.

03. 조건부 에지로 그래프 구성하기

python★ route_tools + 순환 에지
def route_tools(state: State):
    if messages := state.get("messages", []):
        ai_message = messages[-1]
    else:
        raise ValueError(f"No messages found in input state to tool_edge: {state}")

    if hasattr(ai_message, "tool_calls") and len(ai_message.tool_calls) > 0:
        return "tools"
    return END

graph_builder.add_conditional_edges(
    source="chatbot",
    path=route_tools,
    path_map={"tools": "tools", END: END},
)
graph_builder.add_edge("tools", "chatbot")   # 도구 실행 후 챗봇으로 복귀 (순환)
graph_builder.add_edge(START, "chatbot")
graph = graph_builder.compile()
START→ chatbot
route_toolstool_calls 있음 → tools / 없음 → END
tools→ chatbot으로 복귀
★ 핵심 — 순환 구조가 에이전트의 본질

tools → chatbot 에지가 만드는 순환 구조 덕분에 LLM은 도구 결과를 보고 다시 판단해서 추가 도구 호출을 하거나 최종 응답을 낸다. 조건부 에지는 단일 노드에서 시작해야 하며, 사전 구축된 tools_condition도 같은 방식으로 도구 호출이 없으면 __end__를 반환한다.
