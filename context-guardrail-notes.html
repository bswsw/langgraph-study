CHAPTER 07

컨텍스트 엔지니어링

에이전트가 매 호출·매 도구 실행·매 턴 사이에 무엇을 읽고 쓰는지를 설계하는 기술. 모델 / 도구 / 라이프사이클, 세 가지 컨텍스트 타입과 런타임 컨텍스트 / 상태 / Store, 세 가지 데이터 소스를 조합해 동적 프롬프트·도구 필터링·모델 선택·구조화 출력을 구현합니다.

CHAPTER 08

가드레일

에이전트가 안전한 범위 안에서만 동작하도록 입력·도구 실행·최종 응답을 점검하는 보호 장치. 빠르고 값싼 결정론적 검사와 느리지만 정교한 모델 기반 검사를 계층으로 쌓아 PII 유출, 프롬프트 인젝션, 유해 콘텐츠를 막습니다.

💭
Claude의 의견 · 책 내용 아님 7장과 8장은 사실 한 세트로 보는 게 맞다고 생각합니다. 컨텍스트를 정교하게 설계할수록 에이전트가 다루는 정보(개인 선호도, 인증 상태, 히스토리)도 풍부해지는데, 그만큼 8장의 가드레일 없이는 유출됐을 때 피해 범위도 커집니다. 반대로 가드레일만 촘촘히 쌓고 컨텍스트 설계가 부실하면 애초에 쓸모없는 응답을 안전하게 걸러내는 데 그칩니다. 두 장을 따로 공부하기보다, 컨텍스트를 하나 추가할 때마다 "이게 새어나가면 어떻게 되지"를 함께 물어보는 습관을 들이길 추천합니다.
CH.07

컨텍스트 엔지니어링

학습 목표 — 모델 컨텍스트, 도구 컨텍스트, 라이프사이클 컨텍스트의 역할을 이해하고, 런타임 컨텍스트·상태·Store를 활용해 필요한 정보를 전달하는 방법을 익힌다. 동적 프롬프트, 도구 필터링, 모델 선택, 요약을 조합해 실제 환경에서 더 안정적으로 동작하는 에이전트를 구성한다.
대부분의 에이전트 실패는 LLM 능력 부족이 아니라 올바른 컨텍스트가 전달되지 않아서 발생합니다.

01

컨텍스트의 종류

에이전트는 세 가지 컨텍스트를 구분해 관리합니다.

유형지속성제어 범위포함 내용
모델 컨텍스트일시적단일 LLM 호출지시사항, 메시지 기록, 도구, 응답 형식
도구 컨텍스트영구적상태 · Store 읽기/쓰기도구가 액세스·생성하는 모든 데이터
라이프사이클 컨텍스트영구적단계 사이 훅요약, 가드레일, 로깅 등 교차 관심사

일시적 컨텍스트는 LLM이 단일 호출에서만 보는 내용이고, 영구적 컨텍스트는 라이프사이클 훅·도구 쓰기를 통해 여러 턴에 걸쳐 상태나 Store에 반영됩니다.

02

데이터 소스

세 가지 컨텍스트 유형은 아래 세 데이터 소스를 읽고 씁니다. 소스를 잘못 고르면 정보 범위가 맞지 않거나 불필요한 데이터가 전달되어 성능이 저하됩니다.

데이터 소스다른 이름범위예시
런타임 컨텍스트정적 구성대화 범위사용자 ID, API 키, DB 연결 권한
상태(State)단기 메모리대화 범위현재 메시지, 업로드된 파일, 인증 상태
Store장기 메모리대화 간 공유사용자 선호도, 추출된 인사이트, 기록
03

모델 컨텍스트

모델 호출에 들어가는 시스템 프롬프트 · 메시지 · 도구 · 모델 · 응답 형식 다섯 요소를 제어합니다. 핵심 데코레이터는 두 가지입니다.

데코레이터시점용도
@dynamic_prompt모델 호출 직전런타임에 시스템 프롬프트를 동적으로 생성
@wrap_model_call모델 호출을 감쌈메시지 · 도구 · 모델 · 응답 형식을 request.override()로 수정
  • 상태 기반 프롬프트 — 메시지 수가 10개를 넘으면 더 간결하게 응답하도록 지시 (대화 피로도 감지)
  • Store 기반 프롬프트 — store.get(("preferences",), user_id)로 저장된 커뮤니케이션 스타일을 읽어 개인화
  • 런타임 컨텍스트 기반 프롬프트 — request.runtime.context.user_role로 admin/viewer 역할별 RBAC 프롬프트 조정
  • 메시지 주입 — 업로드된 파일 메타데이터를 request.override(messages=...)로 최근 메시지 앞에 삽입
  • 도구 필터링 — 인증 상태·대화 길이·역할에 따라 request.tools를 좁혀 RBAC 구현
  • 모델 선택 — 대화 길이에 따라 저비용/고성능 모델을 request.override(model=...)로 전환
  • 구조화된 출력 — Pydantic 모델을 response_format으로 지정해 검증된 필드로 응답을 강제
state_aware_prompt — 메시지 수에 따라 시스템 프롬프트 동적 조정03-LangGraph-Context-Engineering.ipynb
@dynamic_prompt
def state_aware_prompt(request: ModelRequest) -> str:
    message_count = len(request.messages)
    base = "You are a helpful assistant."
    # 대화가 10턴을 넘으면 더 간결하게 응답하도록 유도
    if message_count > 10:
        base += "\nThis is a long conversation - be extra concise."
    return base

agent = create_agent(model=model, tools=[search_tool], middleware=[state_aware_prompt])
context_based_tools — 런타임 역할에 따른 RBAC 도구 필터링03-LangGraph-Context-Engineering.ipynb
@wrap_model_call
def context_based_tools(request, handler):
    user_role = request.runtime.context.user_role
    if user_role == "editor":
        tools = [t for t in request.tools if t.name != "delete_data"]
        request = request.override(tools=tools)
    elif user_role != "admin":
        tools = [t for t in request.tools if t.name == "read_data"]
        request = request.override(tools=tools)
    return handler(request)
💭
Claude의 의견 · 책 내용 아님 일곱 가지 기법 중 실무에서 가장 먼저 넣어볼 만한 건 개인적으로 도구 필터링(RBAC)이라고 봅니다. 동적 프롬프트나 모델 선택은 효과를 체감하기 어려운 반면, 도구 필터링은 위험한 도구를 애초에 호출 후보에서 제외하는 효과가 명확하고 8장의 가드레일과도 가장 직접적으로 맞닿아 있습니다.

도구 함수에 runtime: ToolRuntime 매개변수를 추가하면 LangGraph가 자동으로 주입합니다. 도구는 읽기·쓰기를 모두 수행할 수 있는 유일한 컨텍스트입니다.

def authenticate_user(password: str, runtime: ToolRuntime) -> Command:

        return Command(update={
            "authenticated": True,
            "messages": [ToolMessage(content="Authentication successful", tool_call_id=tool_call_id)],
        })
    return Command(update={"authenticated": False, "messages": [...]})

CH.08

가드레일

학습 목표 — 빠른 규칙 기반 검사와 모델 기반 검증을 함께 설계해, 실제 서비스 환경에서 신뢰할 수 있는 에이전트 보호 구조를 구성한다. 도로의 가드레일이 차량이 위험한 곳으로 빠지지 않도록 막아주듯, AI 가드레일은 부적절한 입력을 차단하고 민감한 정보를 보호하며 출력 품질을 보장합니다.

  • 개인정보(PII) 유출 방지 — 이메일, 신용카드 번호, 전화번호 등이 노출되지 않도록 탐지·처리
  • 프롬프트 인젝션 공격 탐지 및 차단 — 시스템 프롬프트를 우회하려는 시도를 사전에 감지
  • 부적절하거나 유해한 콘텐츠 차단 — 폭력·혐오 표현 필터링
  • 비즈니스 규칙 및 규정 준수 요구사항 강제
  • 출력 품질 및 정확성 검증

02

내장 가드레일 — PII 탐지

PIIMiddleware는 이메일·신용카드·전화번호 등 다양한 PII 타입을 탐지하고, 4가지 처리 전략 중 하나로 대응합니다.

전략동작예시
redact[REDACTED_TYPE]으로 완전히 대체john@example.com → [REDACTED_EMAIL]
mask부분적으로 가림4532-1234-5678-9010 → ****-9010
hash결정론적 해시로 대체 (추적 가능성 유지)192.168.1.1 → <ip_hash:a1b2c3d4>
block탐지 시 예외 발생, 처리 즉시 중단API 키 탐지 → Exception

내장 PII 타입: email · credit_card(Luhn 검증) · ip · mac_address · url. 정규식 detector를 직접 넘기면 API 키, 한국 전화번호(010-\d{4}-\d{4}) 같은 커스텀 패턴도 탐지합니다.

여러 PIIMiddleware를 배열에 나열 → 순서대로 독립 실행04-LangGraph-Guardrail.ipynb
agent = create_agent(
    model=model, tools=[customer_service_tool],
    middleware=[
        PIIMiddleware("email", strategy="redact", apply_to_input=True),
        PIIMiddleware("credit_card", strategy="mask", apply_to_input=True),
    ],
)
ResultMy email is [REDACTED_EMAIL] and credit card is ****-****-****-6467.
💭
Claude의 의견 · 책 내용 아님 네 가지 전략 중 실무에서 가장 자주 쓰게 되는 건 redact와 mask일 거라고 생각합니다. hash는 "동일 값인지는 추적하고 싶지만 원본은 감춰야 하는" 특수한 상황에서만 필요하고, block은 정상 요청까지 막을 위험이 있어 신중하게 적용해야 한다고 봅니다.
03

Human-in-the-Loop

민감한 작업 실행 전 사람의 승인을 요구하는 가장 효과적인 가드레일. interrupt_on에 도구 이름과 승인 필요 여부를 매핑합니다.

send_email_tool · delete_database_tool만 승인 필요, search_tool은 자동 승인04-LangGraph-Guardrail.ipynb
agent = create_agent(
    model=model, tools=[search_tool, send_email_tool, delete_database_tool],
    middleware=[
        HumanInTheLoopMiddleware(interrupt_on={
            "send_email_tool": True,
            "delete_database_tool": True,
            "search_tool": False,
        }),
    ],
    checkpointer=InMemorySaver(),  # 재개를 위해 상태 지속성 필요
)

# 승인 후 Command(resume=...)로 동일 thread_id에 재개
invoke_graph(agent, Command(resume={"decisions": [{"type": "approve"}]}), config=config)

도구 호출 직전 __interrupt__ 노드에서 실행이 일시 중지되고, 승인이 전달되면 HumanInTheLoopMiddleware.after_model에서 재개됩니다.

04

커스텀 가드레일

내장 가드레일로 부족하면 직접 구현합니다. 두 가지 방식이 있고, 필요에 따라 선택합니다.

@before_agent / @after_agentAgentMiddleware 클래스
적합한 경우단순한 검증 로직설정 가능한 매개변수, 상태 유지 필요
장점간결하고 빠르게 적용재사용성 높음, 여러 훅 조합 가능
종료 제어can_jump_to=["end"] 옵션으로 트리거 시 즉시 에이전트 종료
  • @before_agent — 에이전트 실행 전 요청 검증 (인증, 속도 제한, 금지어 필터링)
  • @after_agent — 최종 응답을 사용자에게 반환하기 전 검증 (모델 기반 안전성 평가에 적합)
  • 클래스 기반은 @hook_config(can_jump_to=[...])로 훅의 동작 방식을 설정
ContentFilterMiddleware — 재사용 가능한 클래스 기반 결정론적 필터04-LangGraph-Guardrail.ipynb
class ContentFilterMiddleware(AgentMiddleware):
    def __init__(self, banned_keywords: list[str]):
        super().__init__()
        self.banned_keywords = [kw.lower() for kw in banned_keywords]

    @hook_config(can_jump_to=["end"])
    def before_agent(self, state, runtime) -> dict | None:
        content = state["messages"][0].content.lower()
        for keyword in self.banned_keywords:
            if keyword in content:
                return {"messages": [{"role": "assistant", "content": "..."}], "jump_to": "end"}
        return None  # None 반환 시 정상 진행

07

가드레일 설계 모범 사례

① 계층화된 방어 — 한 계층이 실패해도 다른 계층이 보호할 수 있도록 설계. 순서가 곧 성능입니다.

순서계층속도/비용역할
1결정론적 필터빠름/저비용키워드 매칭, 정규표현식으로 명백한 위반 조기 차단
2PII 보호빠름/저비용개인정보 탐지 및 처리
3모델 기반 검증느림/고비용LLM을 사용한 의미론적 안전성 평가

② 성능 고려사항 — 빠른 검사를 먼저 실행해 명백한 위반을 조기 차단하면, 느린 LLM 호출 자체가 발생하지 않아 비용을 절감합니다. 트래픽이 많은 프로덕션 환경에서 특히 중요합니다.

✅ 좋은 예 — 결정론적 필터 → 모델 기반 검증 순서. 명백한 위반은 LLM 호출 전 차단.
🚫 나쁜 예 — 느린 모델 기반 검증을 먼저 실행하면 모든 요청에 불필요한 LLM 호출 비용이 발생.

③ 명확한 오류 메시지 — "요청을 처리할 수 없습니다" 같은 모호한 메시지 대신, 왜 차단되었는지와 대안을 함께 안내해야 사용자 경험이 저해되지 않습니다.

④ 로깅 및 모니터링 — 가드레일이 트리거될 때 타임스탬프, 사용자 정보, 차단 사유(민감 정보는 제외)를 로깅합니다.

💭
Claude의 의견 · 책 내용 아님 책이 제시하는 순서(빠른 필터 → PII → 모델 기반 검증)는 합리적인 기본값이지만 절대적인 정답은 아니라고 생각합니다. 실제로는 어떤 유형의 요청이 위험한 비율이 높은지 로그로 먼저 확인한 뒤, 자신의 트래픽 패턴에 맞춰 순서와 강도를 조정하는 편이 더 낫다고 봅니다.
