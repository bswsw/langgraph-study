CHAPTER 15

중간 단계의 상태 수동 업데이트하기

에이전트는 질문을 받아 도구 호출을 만들고, 도구 결과를 다시 LLM에 넘겨 답을 만든다. 그런데 LLM이 만든 검색 쿼리가 부적절하거나 도구가 돌려준 결과를 그대로 쓰기 어려운 경우가 있다. 이 장은 도구 실행 직전에 그래프를 멈추고, 상태를 사람이 직접 고친 뒤 이어서 실행하는 방법을 다룬다. 더 나아가 체크포인트에 저장된 과거 스냅샷으로 돌아가 상태를 바꾸고 다시 실행(리플레이)하는 방법까지 살펴본다.

★ 핵심 — 세 가지 개입 방식
  • 도구 출력 바꾸기 — 검색을 실제로 하지 않고, 사람이 쓴 결과를 ToolMessage로 주입한다. (04절)
  • 도구 입력 바꾸기 — LLM이 만든 tool_calls의 검색 쿼리를 고친 뒤, 실제 검색이 실행되게 한다. (05–06절)
  • 과거 시점 바꾸기 — get_state_history로 과거 체크포인트를 골라 수정하고 그 시점부터 다시 실행한다. (07절)

세 방식 모두 get_state로 확인 → update_state로 수정 → stream(None, ...)으로 재개 순서로 진행한다.

STEP 1stream(..., interrupt_before=["tools"])
STEP 2get_state(config)로 마지막 메시지 확인
STEP 3update_state(config, {...}, as_node=...)
STEP 4stream(None, config)로 이어서 실행

01–03 · 그래프 정의, 인터럽트 설정, 현재 상태 분석

그래프 자체는 앞 장의 에이전트(chatbot ↔ tools)와 같다. 이번 장에서 중요한 차이는 두 가지다.

  • MemorySaver 체크포인터를 붙인다. 체크포인터가 있어야 인터럽트로 멈추고, 상태를 고치고, 다시 이어갈 수 있다.
  • bind_tools(tools, parallel_tool_calls=False)로 도구 호출을 순차적으로 처리하게 한다.
07-LangGraph-Manual-State-Update.ipynb · 그래프 구성 (요약)★ 핵심
class State(TypedDict):
    messages: Annotated[list, add_messages]

tool = TavilySearch(max_results=1)
llm = init_chat_model("claude-sonnet-4-5")
llm_with_tools = llm.bind_tools([tool], parallel_tool_calls=False)

def chatbot(state: State):
    return {"messages": [llm_with_tools.invoke(state["messages"])]}

graph_builder = StateGraph(State)
graph_builder.add_node("chatbot", chatbot)
graph_builder.add_node("tools", ToolNode(tools=[tool]))
graph_builder.add_conditional_edges("chatbot", tools_condition)
graph_builder.add_edge("tools", "chatbot")
graph_builder.add_edge(START, "chatbot")
graph_builder.add_edge("chatbot", END)

graph = graph_builder.compile(checkpointer=MemorySaver())

interrupt_before는 디버거의 브레이크포인트처럼 지정한 노드가 실행되기 직전에 그래프를 멈춘다. 어떤 노드에 걸 수 있는지는 graph.channels로 확인할 수 있다.

채널 목록 확인 → tools 직전에서 멈추기
list(graph.channels)
# ['messages', '__start__', '__pregel_tasks', 'branch:to:chatbot', 'branch:to:tools']

config = RunnableConfig(configurable={"thread_id": "1"})
events = graph.stream(
    input=State(messages=[("user", "LangGraph가 무엇인지 조사하여 알려주세요!")]),
    config=config,
    interrupt_before=["tools"],
    stream_mode="values",
)
# → AI Message: Tool Calls: tavily_web_search(query: "LangGraph란 무엇인가") 에서 멈춤

멈춘 상태에서 graph.get_state(config).values["messages"][-1]을 보면, 원래 질문 "LangGraph가 무엇인지 조사하여 알려주세요!"가 LLM에 의해 "LangGraph란 무엇인가"로 압축된 것을 알 수 있다. 이런 쿼리로는 원하는 검색 결과가 안 나올 수 있으니 사람이 개입할 이유가 생긴다.

◆ 책 외 보충

parallel_tool_calls=True면 인터럽트는 어떻게 될까

책은 False로 둔 이유를 "도구 호출을 순차적으로 처리"라고만 설명한다. True면 LLM이 한 AIMessage에 도구 호출을 여러 개 담을 수 있는데, 인터럽트 자체는 정상 동작한다. 다만 인터럽트는 노드 단위로 걸리고 ToolNode는 여러 호출을 한 스텝에서 같이 실행하므로, 호출과 호출 사이에서는 멈출 수 없다.

설정멈춘 횟수멈춘 시점
interrupt_before=["tools"]1번두 호출 모두 실행 전 (next=('tools',))
interrupt_after=["tools"]1번두 호출 모두 실행 후 (ToolMessage 2개 생성 뒤)

문제는 멈춘 뒤 상태를 고칠 때다. 이 장의 수정 코드는 "호출이 항상 1개"라는 전제로 tool_calls[0]만 다룬다.

멈춘 뒤 하는 일True여도 괜찮나
상태 확인만 하고 stream(None)으로 재개괜찮음
호출 목록을 보고 진행/중단만 판단괜찮음
결과 직접 주입 (04절)주의 ToolMessage를 하나만 넣고 as_node="tools"로 업데이트하면 그래프는 tools가 끝난 것으로 보고 chatbot으로 넘어간다. 나머지 호출은 결과 없이 남고, 다음 LLM 호출에서 "tool_use에 대응하는 tool_result가 없다"는 API 오류가 난다. → 모든 tool_call_id에 ToolMessage를 넣어야 한다.
쿼리 수정 (06·07절)주의 tool_calls=[new_tool_call]는 목록을 통째로 바꾸므로 다른 호출이 오류 없이 사라진다. → 목록을 복사해 해당 항목만 고친다.
참고 구현 (책 예제 아님) · 호출이 여러 개일 때
# 결과 주입: 모든 호출에 ToolMessage
graph.update_state(config, {"messages": [
    ToolMessage(content=..., tool_call_id=tc["id"]) for tc in last_message.tool_calls
]}, as_node="tools")

# 쿼리 수정: 목록 복사 후 바꿀 항목만
new_tool_calls = [tc.copy() for tc in existing_message.tool_calls]
new_tool_calls[1]["args"] = {"query": "..."}
new_message = AIMessage(content=existing_message.content,
                        tool_calls=new_tool_calls, id=existing_message.id)

정리하면 False는 인터럽트가 동작하게 하려는 설정이라기보다, 멈출 때마다 호출이 1개가 되도록 고정해 상태 수정 코드를 단순하게 유지하려는 설정으로 볼 수 있다(해석). 책 코드를 그대로 쓴다면 False를 유지한다.

출처: 직접 실행 테스트 — langgraph 1.2.11 / langgraph-prebuilt 1.1.0, 도구 호출 2개를 내는 가짜 chatbot으로 확인 (API 오류 부분은 Anthropic tool use 규칙 기준, 실행 확인 안 함)

04 · 사람의 개입으로 검색 결과 수정하기 (도구 출력 바꾸기)

웹 검색 결과에는 잘못된 정보가 섞일 수 있고, 이는 최종 답변 품질에 바로 영향을 준다. 그래서 실제 검색을 하지 않고 사람이 검증한 내용을 ToolMessage로 직접 넣는다.

★ tool_call_id는 반드시 맞춰야 한다

tool_call_id는 LLM이 도구 호출을 요청할 때 만든 고유 식별자다. 이 ID로 "어떤 도구 호출에 대한 응답인지"를 매칭한다. 주입하는 ToolMessage의 tool_call_id가 원래 호출과 다르면 LLM이 응답을 올바르게 처리하지 못한다.

가짜 검색 결과를 ToolMessage로 만들어 주입★ 핵심
from langchain_core.messages import AIMessage, ToolMessage

last_message = graph.get_state(config).values["messages"][-1]
tool_call_id = last_message.tool_calls[0]["id"]   # toolu_01PeVf89...

new_messages = [
    ToolMessage(content=modified_search_result, tool_call_id=tool_call_id),
]

graph.update_state(
    config,
    {"messages": new_messages},   # add_messages 리듀서 → 기존 목록에 "추가"됨
    as_node="tools",              # tools 노드가 실행된 것처럼 취급
)

update_state 메서드

update_state는 주어진 값으로 그래프 상태를 갱신하는 핵심 메서드다. 지정한 as_node에서 값이 나온 것처럼 동작한다. 체크포인터로 이전 상태를 불러와 새 상태를 저장하므로 버전 관리와 지속성이 보장되고, 그래프 단계를 시뮬레이션하므로 trace도 남는다.

매개변수의미
config실행 구성(RunnableConfig)을 지정한다.
values업데이트할 값을 딕셔너리 형태로 전달한다. messages에는 add_messages 리듀서가 적용되어 있으므로 기존 메시지를 덮어쓰지 않고 새 메시지가 추가된다.
as_node값의 출처로 간주할 노드 이름. 기본값 None이면 마지막으로 실행된 노드가 자동 선택된다.
반환값업데이트된 상태를 가리키는 RunnableConfig (thread_id, checkpoint_id 포함)

as_node="tools"로 업데이트하면 다음 노드는 tools 다음인 chatbot이 된다 (snapshot.next == ('chatbot',)). 이제 graph.stream(None, config)처럼 입력에 None을 주면 상태에 아무것도 추가하지 않고 이어서 실행하며, chatbot은 주입된 ToolMessage를 바탕으로 최종 답을 만든다. 최종 답변 자체를 고치고 싶다면 as_node="chatbot"으로 AIMessage를 넣으면 된다.

다 끝난 뒤 스냅샷의 메시지는 HumanMessage → AIMessage(도구 호출) → ToolMessage(수정된 결과) → AIMessage(최종 답) 순서이고, snapshot.next가 빈 튜플 ()이면 실행이 끝난 것이다.

05–06 · 인터럽트 후 검색 쿼리 수정하기 (도구 입력 바꾸기)

04절은 도구의 출력을 바꿨고, 이번에는 도구의 입력, 즉 LLM이 만든 쿼리를 바꾼다. 도구가 실제로 실행되므로 검색 결과의 실시간성은 유지하면서 쿼리 품질은 사람이 보장할 수 있다는 장점이 있다. 새 thread_id로 "LangGraph에 대해서 배워보고 싶습니다. 유용한 자료를 추천해 주세요!"를 실행하고 tools 직전에서 멈춘다.

★ 핵심 — add_messages는 ID로 교체/추가를 가른다
같은 ID

기존 메시지를 새 메시지로 교체(Replace)

다른 ID / ID 없음

리스트 끝에 새 메시지로 추가(Append)

그래서 도구 호출 쿼리를 바꿀 때는 새 AIMessage의 id를 기존 메시지 id와 같게 둬야 한다. 그래야 메시지가 하나 더 쌓이지 않고 기존 호출이 수정된다.

tool_calls 복사 → 쿼리만 수정 → 같은 id로 덮어쓰기★ 핵심
snapshot = graph.get_state(config)
existing_message = snapshot.values["messages"][-1]
# tool_calls[0] = {'name': 'tavily_web_search',
#                  'args': {'query': 'LangGraph 튜토리얼 학습 자료 추천'},
#                  'id': 'toolu_012nV7...', 'type': 'tool_call'}

new_tool_call = existing_message.tool_calls[0].copy()   # name/id/type 유지
new_tool_call["args"] = {"query": "LangGraph site:teddylee777.github.io"}

new_message = AIMessage(
    content=existing_message.content,
    tool_calls=[new_tool_call],
    id=existing_message.id,   # 같은 ID → 추가가 아니라 교체
)

graph.update_state(config, {"messages": [new_message]})   # as_node 생략 → 마지막 업데이트 노드
graph.stream(None, config, stream_mode="values")       # tools가 수정된 쿼리로 실제 검색

업데이트 후 tool_calls를 다시 보면 args의 query가 'LangGraph 튜토리얼 학습 자료 추천' 대신 'LangGraph site:teddylee777.github.io'로 바뀌어 있다. 이어서 같은 스레드에 추가 질문을 보내 전체 대화 흐름을 확인한다.

같은 스레드에서 추가 질문 → 최종 응답 확인
events = graph.stream(
    {"messages": ("user", "내가 지금까지 배운 내용에 대해서 매우 친절하고 정성스럽게 한국어로 "
                          "답변해줘! 출처를 반드시 포함해줘!")},
    config,
    stream_mode="values",
)
for event in events:
    if "messages" in event:
        event["messages"][-1].pretty_print()

graph.get_state(config).values["messages"][-1].pretty_print()   # 수정된 쿼리 기반 최종 응답

tool_calls[0]의 속성은 name(도구 이름), args(검색 쿼리), id(도구 호출 ID), type(tool_call)이다. copy()로 복사하면 id가 바뀌지 않아 의도치 않게 메시지가 추가되는 문제를 막을 수 있다.

◆ 책 외 보충

dict.copy()는 얕은 복사다

책 예제는 new_tool_call["args"] = {...}로 args 딕셔너리를 통째로 바꾸기 때문에 안전하다. 그런데 new_tool_call["args"]["query"] = "..."처럼 안쪽 값을 직접 고치면, 얕은 복사라서 원본 메시지의 args도 같이 바뀐다. 과거 스냅샷 객체까지 오염될 수 있으니, 안쪽을 고칠 생각이면 copy.deepcopy()를 쓰는 편이 안전하다. 같은 이유로 config.copy()도 configurable 딕셔너리는 원본과 공유한다.

메시지 삭제는 RemoveMessage

add_messages는 교체·추가 외에 삭제도 지원한다. update_state(config, {"messages": [RemoveMessage(id=msg.id)]})로 특정 메시지를 지울 수 있다. 단, 도구 호출 AIMessage만 지우고 짝이 되는 ToolMessage를 남기면(또는 그 반대) 모델 API가 오류를 낼 수 있으니 짝을 같이 정리해야 한다.

출처: Python 표준 라이브러리 copy 모듈 · langgraph.graph.message.add_messages 동작

07 · 지난 스냅샷의 결과 수정 및 리플레이하기

리플레이(Replay)는 특정 과거 체크포인트로 되돌아가 상태를 고친 뒤 해당 노드부터 다시 진행하는 것이다. 영화를 특정 장면으로 되감아 다른 결말을 찍는 것과 비슷하다. 디버깅, A/B 테스트, 에이전트 의사결정을 소급해서 고쳐야 할 때 쓸모가 있다.

메시지가 2개인 시점(= 도구 실행 직전) 찾기
to_replay_state = None
for state in graph.get_state_history(config):    # 상태 기록 가져오기
    messages = state.values["messages"]
    if len(messages) > 0:
        print("메시지 수:", len(messages), "다음 노드:", state.next)
        if len(messages) == 2:                     # Human + AI(도구 호출)
            to_replay_state = state

◆ 책 외 보충

과거 시점 업데이트는 "덮어쓰기"가 아니라 "포크(fork)"다

과거 체크포인트에 update_state를 하면 그 체크포인트가 고쳐지는 게 아니라, 그 체크포인트를 부모로 하는 새 체크포인트가 만들어진다. 원래 실행 이력은 그대로 남고, 같은 스레드 안에 갈래가 하나 더 생기는 구조다. 그래서 같은 시점에서 여러 쿼리를 시험해 보는 A/B 비교가 가능하다.

원래 이력 input→ Human+AI(쿼리 A)→ Tool(결과 A)→ AI(답 A)
포크 Human+AI(쿼리 A)↳ AI(쿼리 B) · 새 checkpoint_id→ Tool(결과 B)→ AI(답 B) = 스레드의 최신 상태

config에 checkpoint_id가 있느냐 없느냐

  • get_state_history는 최신 체크포인트부터 과거 순서로 스냅샷을 돌려준다.
  • {"configurable": {"thread_id": ...}}처럼 checkpoint_id가 없는 config는 그 스레드의 가장 최근 체크포인트를 가리킨다. 결과 확인에 원래 config를 쓰면 포크된 최신 상태가 나오는 이유다.
  • to_replay_state.config나 updated_state처럼 checkpoint_id가 있는 config는 그 특정 시점을 가리킨다. update_state가 돌려준 checkpoint_id는 방금 만들어진 새 체크포인트의 ID다.

수정 없이 다시 돌리기 = 순수 리플레이

상태를 바꾸지 않고 graph.stream(None, to_replay_state.config)처럼 과거 체크포인트 config로 바로 실행하면, 그 체크포인트 이전 단계는 저장된 결과를 재사용하고 이후 단계만 다시 실행한다. LLM 호출은 다시 일어나므로 결과가 이전과 똑같다는 보장은 없다.

정적 인터럽트 vs 동적 interrupt()

이 장에서 쓴 interrupt_before/interrupt_after는 노드 단위로 거는 정적 인터럽트다. LangGraph 공식 문서는 정적 인터럽트를 주로 디버깅·단계별 점검용으로 권장하고, 실제 HITL 워크플로에는 노드 안에서 조건부로 멈추는 interrupt() 함수와 Command(resume=...) 조합을 권장한다. (16장 보충 박스에 예시)

CHAPTER 16

HumanRequest 패턴: 사람에게 위임하는 그래프

15장은 모든 도구 호출 앞에서 멈췄다. 하지만 매번 멈출 필요는 없다. 이 장은 LLM이 "사람의 도움이 필요하다"고 판단한 순간에만 그래프를 human 노드로 보내는 패턴을 다룬다. 핵심 도구는 상태에 넣는 커스텀 플래그와, 실제로 실행되지 않고 신호 역할만 하는 HumanRequest 도구다.

★ 핵심 — 동작 순서
  1. LLM이 HumanRequest 도구를 호출하면 chatbot이 상태의 ask_human을 True로 바꾼다.
  2. 라우터가 ask_human을 보고 human 노드로 보낸다. interrupt_before=["human"]이라 그 직전에 멈춘다.
  3. 전문가 역할을 맡은 사람이 답변을 작성하면, 이를 create_response로 ToolMessage로 만들어 update_state로 상태에 추가한다.
  4. stream(None, config)로 재개 → human 노드는 플래그만 끄고 → chatbot이 전문가 답을 바탕으로 최종 답을 만든다.

01 · 상태 정의, HumanRequest 스키마, 챗봇 노드

LangGraph 상태는 메시지만 담는 공간이 아니다. 커스텀 필드를 추가하면 현재 실행 조건을 더 세밀하게 표현하고, 그 값으로 흐름을 제어할 수 있다. 여기서는 필드마다 업데이트 전략이 다르다는 점이 중요하다.

필드리듀서업데이트 방식
messagesadd_messages누적(append), 같은 ID는 교체
ask_human없음단순 덮어쓰기(overwrite) — 마지막으로 반환된 값이 남는다
08-LangGraph-State-Customization.ipynb · 상태와 HumanRequest★ 핵심
class State(TypedDict):
    messages: Annotated[list, add_messages]
    ask_human: bool          # 사람에게 질문할지 여부

class HumanRequest(BaseModel):
    """Forward the conversation to an expert. Use when you can't assist directly or the
    user needs assistance that exceeds your authority.
    To use this function, pass the user's 'request' so that an expert can provide
    appropriate guidance.
    """
    request: str

tool = TavilySearch(max_results=3)
tools = [tool, HumanRequest]               # LLM에게는 둘 다 보여 준다
llm_with_tools = init_chat_model("claude-sonnet-4-5").bind_tools(tools)

def chatbot(state: State):
    response = llm_with_tools.invoke(state["messages"])
    ask_human = False
    if response.tool_calls and response.tool_calls[0]["name"] == HumanRequest.__name__:
        ask_human = True
    return {"messages": [response], "ask_human": ask_human}

HumanRequest는 Pydantic 모델이라 bind_tools에 바로 넘길 수 있다. LangChain이 모델을 도구 스키마로 자동 변환하므로 @tool 데코레이터가 없어도 LLM이 도구로 인식한다.

주의 — HumanRequest는 ToolNode에 넣지 않는다

graph_builder.add_node("tools", ToolNode(tools=[tool]))처럼 실제 도구만 넣는다. HumanRequest는 흐름을 바꾸는 신호일 뿐이라, ToolNode에 넣으면 그래프가 이를 실제로 실행하려다 오류가 난다.

02 · human 노드, 조건부 라우팅, 컴파일

human 노드는 사람의 개입이 필요할 때 실행되며, 인터럽트를 트리거하고 사람의 응답을 기다린 뒤 대화를 이어 간다. 실제 프로덕션에서는 이 패턴으로 AI가 답하기 어려운 질문이나 민감한 의사결정이 필요한 상황에서 전문가에게 대화를 자동으로 이관하는 워크플로를 만들 수 있다.

human 노드는 인터럽트를 트리거하는 자리 표시자(placeholder)다. 사람이 인터럽트 동안 상태를 업데이트하지 않으면 "No response from human."이라는 기본 ToolMessage를 넣어, LLM이 요청은 했지만 답을 못 받았다는 걸 알게 한다. 그리고 ask_human을 False로 되돌려 같은 노드를 다시 방문하지 않게 한다.

create_response · human_node · select_next_node★ 핵심
def create_response(response: str, ai_message: AIMessage):
    return ToolMessage(content=response, tool_call_id=ai_message.tool_calls[0]["id"])

def human_node(state: State):
    new_messages = []
    if not isinstance(state["messages"][-1], ToolMessage):   # 사람 응답이 없을 때만
        new_messages.append(
            create_response("No response from human.", state["messages"][-1])
        )
    return {"messages": new_messages, "ask_human": False}     # 플래그 해제

def select_next_node(state: State):
    if state["ask_human"]:
        return "human"
    return tools_condition(state)          # "tools" 또는 END

graph_builder.add_node("human", human_node)
graph_builder.add_conditional_edges(
    "chatbot", select_next_node, {"human": "human", "tools": "tools", END: END}
)
graph_builder.add_edge("tools", "chatbot")
graph_builder.add_edge("human", "chatbot")
graph_builder.add_edge(START, "chatbot")

graph = graph_builder.compile(checkpointer=MemorySaver(), interrupt_before=["human"])
★ 왜 마지막 메시지가 ToolMessage인지 확인하나

사람이 인터럽트 중에 update_state로 ToolMessage를 이미 넣었다면, human 노드가 기본 응답을 또 넣으면 안 된다. 이 방어 로직이 없으면 사람의 응답과 "No response" 메시지가 동시에 존재하는 비정상 상태가 된다.

★ 왜 interrupt_after가 아니라 interrupt_before인가

interrupt_after를 쓰면 human 노드의 "No response" 로직이 먼저 실행된 뒤 멈추므로 사람이 개입할 의미가 없어진다. 노드 실행 전에 멈춰야 전문가가 상태를 보고 응답을 넣을 시간이 생긴다.

chatbot → human

HumanRequest 호출 → 전문가에게 도움 요청 (interrupt=before)

chatbot → tools

TavilySearch 호출 → 검색 실행 후 chatbot으로 복귀

chatbot → END

도구 호출 없음 → 바로 답변하고 종료

업데이트 직후 메시지는 사용자 메시지 · HumanRequest 도구 호출 · 전문가 ToolMessage 세 개다. update_state가 반환하는 checkpoint_id는 상태의 특정 시점을 고유하게 식별하는 값으로, 디버깅이나 복구에 쓸 수 있다. 재개하면 human 노드는 이미 ToolMessage가 있으니 메시지를 추가하지 않고 플래그만 끈다. 최종 대화는 Human → AI(HumanRequest) → Tool(전문가 답) → AI("전문가의 답변이 도착했습니다! ...") 순서가 된다.

◆ 책 외 보충

같은 패턴을 interrupt() + Command(resume=...)로 쓰면

책의 방식은 정적 인터럽트로 멈춘 뒤 바깥에서 update_state로 ToolMessage를 직접 만들어 넣는다. 최신 LangGraph에서는 노드 안에서 interrupt()로 멈추고, 재개할 때 넘긴 값을 노드가 그대로 받는 방식을 많이 쓴다. tool_call_id 매칭과 "No response" 방어 로직을 노드 한 곳에 모을 수 있다.

참고 구현 (책 예제 아님)
from langgraph.types import interrupt, Command

def human_node(state: State):
    ai_message = state["messages"][-1]
    request = ai_message.tool_calls[0]["args"]["request"]
    answer = interrupt({"request": request})      # 여기서 멈춤, 재개 시 값이 반환됨
    return {
        "messages": [create_response(answer or "No response from human.", ai_message)],
        "ask_human": False,
    }

graph = graph_builder.compile(checkpointer=MemorySaver())   # interrupt_before 불필요

graph.invoke({"messages": [("user", user_input)]}, config)  # → __interrupt__ 반환
graph.invoke(Command(resume="전문가 답변 ..."), config)      # 답변을 넣고 재개

human 노드로 가는 경로는 책 코드 그대로다. chatbot(HumanRequest 호출 시 ask_human=True), select_next_node(플래그가 켜져 있으면 "human"), human → chatbot 에지는 바꾸지 않고, 위 코드처럼 human_node와 compile 두 곳만 교체한다.

호출실행 흐름
1번째 invoke
(사용자 질문)		chatbot이 HumanRequest 호출 → ask_human=True → select_next_node가 "human" 반환 → human_node 실행 중 interrupt()에서 멈춤 → __interrupt__와 함께 반환 (앱은 여기 담긴 request를 전문가에게 보여 주고 답을 받는다)
2번째 invoke
(Command(resume=...))		human_node가 처음부터 다시 실행 → 이번엔 interrupt()가 전문가 답변을 반환 → ToolMessage 생성, ask_human=False → chatbot이 최종 답 생성 → END
책 (정적 인터럽트)interrupt() 방식
human으로 가는 라우팅같음 — chatbot이 플래그를 켜고 select_next_node가 human으로 보냄
멈추는 곳human 노드 들어가기 전 (interrupt_before)human 노드 안 interrupt() 줄
답변 전달바깥에서 ToolMessage를 만들어 update_state답변 텍스트만 Command(resume=...)로 넘김
"No response" 방어 로직마지막 메시지가 ToolMessage인지 검사불필요 (answer or ...)
재개stream(None, config)invoke(Command(resume=...), config)

주의: 재개되면 노드가 처음부터 다시 실행되므로, interrupt() 앞에 부작용(외부 API 호출 등)을 두지 않는다.

책 코드의 함정 — 병렬 도구 호출

이 장은 15장과 달리 parallel_tool_calls=False를 설정하지 않았다. LLM이 한 응답에서 TavilySearch와 HumanRequest를 함께 호출하면 tool_calls[0]만 검사하므로 HumanRequest를 놓칠 수 있고, human 노드도 첫 번째 호출에만 ToolMessage를 붙인다. 응답이 없는 tool_call이 남으면 다음 LLM 호출에서 Anthropic/OpenAI API가 "tool_use에 대응하는 tool_result가 없다"는 오류를 낸다. 실무에서는 parallel_tool_calls=False를 주거나, any(tc["name"] == "HumanRequest" for tc in response.tool_calls)로 검사하고 모든 호출에 응답을 채워 두는 편이 안전하다.

Pydantic 독스트링 = 도구 설명

Pydantic 모델을 bind_tools에 넘기면 클래스 이름이 도구 이름, 독스트링이 도구 설명, 필드가 인자 스키마가 된다. LLM은 이 설명을 보고 "언제 HumanRequest를 부를지" 판단하므로, 17장의 @tool 독스트링과 같은 원칙으로 용도를 명확히 써야 한다.

CHAPTER 17

ToolNode를 사용하여 도구 호출하기

ToolNode는 메시지 목록이 든 그래프 상태를 받아, 마지막 AIMessage의 tool_calls를 읽고 해당 도구를 실행한 뒤 그래프 상태를 업데이트하는 LangGraph의 사전 구축 컴포넌트(LangChain Runnable 객체)다. 사전 구축 에이전트와 바로 쓸 수 있게 설계되었고, 적절한 리듀서가 있는 messages 키만 있으면 어떤 StateGraph와도 함께 쓸 수 있다. 이 장은 단일/병렬 도구 호출, LLM 연동, 에이전트 그래프 통합, 오류 처리 전략, ToolRuntime을 통한 상태 접근을 차례로 다룬다.

◆ 책 외 보충

14장 BasicToolNode와의 관계

14장에서 직접 만든 BasicToolNode(마지막 메시지의 tool_calls를 돌며 도구를 실행하고 ToolMessage를 만드는 클래스)의 기능을 라이브러리가 제공하는 것이 ToolNode라고 보면 된다. 여기에 병렬 실행, 오류 처리, 상태 주입이 더해져 있다.

출처: 이 저장소의 14장 정리 노트와 비교한 정리
INPUTstate["messages"][-1] = AIMessage(tool_calls=[...])
ToolNodename으로 도구 찾기 → args로 실행
OUTPUT{"messages": [ToolMessage(tool_call_id=...), ...]}

01 · 도구 정의와 ToolNode 초기화

@tool 데코레이터는 함수의 독스트링, 매개변수 이름, 타입 힌트를 분석해 도구 스키마를 자동으로 만든다. 독스트링은 LLM이 도구를 고를 때 보는 핵심 정보라서, 무엇을 하는지·어떤 입력이 필요한지를 짧고 명확하게 써야 한다.

10-LangGraph-ToolNode.ipynb · 도구 두 개와 ToolNode
python_repl_tool = PythonREPLTool()

@tool
def search_news(query: str) -> List[Dict[str, str]]:
    """Google 뉴스에서 키워드로 검색합니다."""
    return GoogleNews().search_by_keyword(query, k=5)

@tool
def python_code_interpreter(code: str):
    """Python 코드를 실행합니다."""
    return python_repl_tool.invoke(code)

tools = [search_news, python_code_interpreter]
tool_node = ToolNode(tools)      # 접수 창구 직원처럼 tool_calls를 보고 해당 도구로 전달

02 · ToolNode 수동 호출 — 단일·병렬

그래프 없이 도구 동작을 빠르게 확인하거나 디버깅하려면 ToolNode만 넣은 테스트 그래프를 만들어 직접 호출한다. 조건은 하나다. 메시지 목록의 마지막이 tool_calls를 가진 AIMessage여야 한다. tool_calls의 각 항목은 name, args, id, type을 가진다.

AIMessage를 손으로 만들어 ToolNode 테스트★ 핵심
test_graph = StateGraph(MessagesState)
test_graph.add_node("tools", tool_node)
test_graph.add_edge(START, "tools")
test_graph.add_edge("tools", END)
test_app = test_graph.compile()

# 단일 호출
msg = AIMessage(content="", tool_calls=[
    {"name": "search_news", "args": {"query": "AI"}, "id": "tool_call_id", "type": "tool_call"},
])
test_app.invoke({"messages": [msg]})

# 병렬 호출 — tool_calls에 여러 개를 넣으면 ToolNode가 함께 실행
msg = AIMessage(content="", tool_calls=[
    {"name": "search_news", "args": {"query": "AI"}, "id": "tool_call_id_1", "type": "tool_call"},
    {"name": "python_code_interpreter", "args": {"code": "print('Hello, World!')"},
     "id": "tool_call_id_2", "type": "tool_call"},
])
test_app.invoke({"messages": [msg]})
주의

마지막 메시지가 AIMessage가 아니거나 tool_calls가 비어 있으면 ToolNode는 오류를 낸다. 수동 테스트 시 형식을 정확히 맞춘다.

병렬 호출은 뉴스 검색과 코드 실행처럼 서로의 결과에 의존하지 않는 작업에 유리하다. 한 도구의 결과를 다른 도구의 입력으로 써야 한다면 순차 호출이 필요하다.

◆ 책 외 보충

ToolNode의 "병렬"은 실제로 어떻게 돌까

설치된 langgraph-prebuilt 소스를 보면, 동기 실행(invoke)은 스레드 풀의 executor.map으로, 비동기 실행(ainvoke)은 asyncio.gather로 여러 tool_call을 동시에 실행한다. 결과 ToolMessage는 tool_calls 순서대로 돌아온다. 따라서 같은 리소스(파일, 전역 변수, PythonREPL 세션 등)를 건드리는 도구들을 병렬로 부르면 경쟁 상태가 생길 수 있다.

03–04 · LLM과 함께, 그리고 에이전트 그래프로

실제로는 AIMessage를 손으로 만들지 않는다. bind_tools()로 모델에 도구를 알려 주면 LLM이 tool_calls가 담긴 AIMessage를 만든다. 이 메시지를 그대로 ToolNode에 넘기면 된다. LLM은 "어떤 도구를 어떤 인자로 호출할지" 결정하고, ToolNode는 실행만 맡는 관심사의 분리(Separation of Concerns) 패턴이다.

LLM ↔ ToolNode 순환 에이전트★ 핵심
model_with_tools = init_chat_model("claude-sonnet-4-5").bind_tools(tools)

ai_message = model_with_tools.invoke("처음 5개의 소수를 출력하는 python code를 작성해줘")
ai_message.tool_calls   # [{'name': 'python_code_interpreter', 'args': {'code': '...'}, ...}]
test_app.invoke({"messages": [ai_message]})    # LLM 결정 → ToolNode 실행

def call_model(state: MessagesState):
    return {"messages": [model_with_tools.invoke(state["messages"])]}

workflow = StateGraph(MessagesState)
workflow.add_node("agent", call_model)
workflow.add_node("tools", tool_node)
workflow.add_edge(START, "agent")
workflow.add_conditional_edges("agent", tools_condition)   # tool_calls 있으면 "tools", 없으면 END
workflow.add_edge("tools", "agent")
app = workflow.compile()

tools_condition은 LLM 응답의 tool_calls 유무만 보고 분기하는 사전 구축 조건 함수라, 분기 로직을 직접 짤 필요가 없다. 테스트 결과 에이전트는 질문 성격에 따라 스스로 판단한다.

질문실행 경로결과
처음 5개의 소수를 출력하는 python code를 작성해줘agent → tools → agent코드 실행 결과 [2, 3, 5, 7, 11]과 코드 설명
search google news about AIagent → tools → agentsearch_news 결과를 정리한 답변
안녕? 반가워agent → END도구 호출 없이 바로 인사

05 · 도구 오류 처리 — handle_tool_errors

ToolNode는 도구 실행 중 발생하는 오류도 자동으로 처리한다. 책에 따르면 기본적으로 handle_tool_errors=True가 설정되어 있어, 예외가 나면 오류 메시지를 ToolMessage로 바꿔 LLM에게 전달하고, LLM은 오류를 인식해 다른 방법을 시도한다. 비활성화하려면 ToolNode(tools, handle_tool_errors=False)로 설정한다. 오류가 처리되면 ToolMessage의 status 필드는 "error"로 설정된다.

설정값동작
True (기본값)모든 오류를 잡아 오류 메시지를 LLM에 전달 책 기준 · 현재 버전은 아래 보충 참고
False오류 처리 비활성화, 예외가 그대로 발생
"커스텀 메시지"오류 시 고정 문자열을 전달
callable예외 객체를 받아 메시지를 만드는 함수 사용
(ValueError, TypeError)지정한 예외 타입만 처리, 나머지는 발생
커스텀 핸들러와 오류 테스트★ 핵심
def custom_error_handler(error: Exception) -> str:
    """오류 타입에 따라 다른 메시지를 반환하는 핸들러"""
    if isinstance(error, ValueError):
        return f"입력값 오류: {error}"
    return f"예상치 못한 오류: {error}"

tool_node_callable = ToolNode(tools, handle_tool_errors=custom_error_handler)

@tool
def error_tool(input: str) -> str:
    """항상 오류를 발생시키는 테스트 도구"""
    raise ValueError(f"잘못된 입력: {input}")

error_tool_node = ToolNode(
    [error_tool],
    handle_tool_errors="도구 실행 중 오류가 발생했습니다. 다른 방법을 시도해 주세요.",
)
# → Tool Message (Name: error_tool): 도구 실행 중 오류가 발생했습니다. 다른 방법을 시도해 주세요.
★ 프로덕션 권장 — Callable 핸들러

오류 타입별로 LLM에게 구체적인 안내를 줄 수 있어 재시도 전략을 고르기 쉽다. 예: 인증 오류엔 "API 키를 확인하세요", 타임아웃엔 "잠시 후 다시 시도하세요".

◆ 책 외 보충

현재 버전의 기본값은 True가 아니다

책은 기본값을 handle_tool_errors=True(모든 오류를 잡음)로 설명한다. 이 프로젝트에 설치된 langgraph 1.2.11 / langgraph-prebuilt 1.1.0에서는 기본값이 _default_handle_tool_errors라는 함수이고, 동작이 다르다.

  • LLM이 잘못된 인자를 넘겨 생긴 ToolInvocationError(스키마 검증 실패) → ToolMessage로 바꿔 LLM에 전달
  • 도구 실행 중 생긴 예외(위 error_tool의 ValueError 등) → 그대로 다시 발생(raise)

즉 아무 설정 없이 쓰면 책의 설명과 달리 실행 오류에서 그래프가 멈춘다. 모든 오류를 LLM에 넘기고 싶다면 handle_tool_errors=True를 명시해야 한다.

Callable 핸들러는 타입 힌트로 잡을 예외를 정한다

핸들러 첫 매개변수의 타입 어노테이션을 보고 처리할 예외 타입을 추론한다(_infer_handled_types). 책 예제처럼 error: Exception이면 모든 예외를, error: ValueError | TypeError로 쓰면 그 두 타입만 잡고 나머지는 발생시킨다.

06 · 도구에서 그래프 상태 접근하기 — ToolRuntime

대화 기록의 길이를 보거나 커스텀 상태 값을 참조하는 등, 도구가 그래프 상태를 읽어야 할 때가 있다. 도구 매개변수에 ToolRuntime을 선언하면 ToolNode가 실행 시점에 자동으로 주입한다. 이 매개변수는 LLM에게 노출되지 않아 도구 스키마에 영향을 주지 않는다. 사무실의 공유 화이트보드(그래프 상태)를 볼 수 있는 열쇠에 비유할 수 있다.

runtime.state로 상태 읽기★ 핵심
from langchain.tools import ToolRuntime

@tool
def get_message_count(runtime: ToolRuntime) -> str:
    """현재 대화의 메시지 수를 반환합니다."""
    messages = runtime.state["messages"]
    return f"현재 대화에 {len(messages)}개의 메시지가 있습니다."

state_tool_node = ToolNode([get_message_count])

test_messages = [
    HumanMessage(content="안녕하세요"),
    AIMessage(content="", tool_calls=[
        {"name": "get_message_count", "args": {}, "id": "state_test_id", "type": "tool_call"},
    ]),
]
# → Node: tools / 현재 대화에 2개의 메시지가 있습니다.
◆ 책 외 보충

ToolRuntime에는 state 말고도 들어 있다

속성내용
state현재 그래프 상태
tool_call_id이번 도구 호출의 ID — 도구에서 직접 ToolMessage를 만들 때 필요
config현재 실행의 RunnableConfig (thread_id 등)

이전 버전 코드에서는 같은 일을 Annotated[dict, InjectedState], Annotated[str, InjectedToolCallId], InjectedStore 어노테이션으로 했다. 지금도 쓸 수 있지만 ToolRuntime 하나로 모아 쓰는 쪽이 간단하다.

읽기만이 아니라 상태 쓰기도: Command 반환

도구가 Command(update={...})를 반환하면 ToolNode가 메시지 외의 상태 필드도 갱신한다. 이때 짝이 되는 ToolMessage를 함께 넣어야 tool_call이 응답 없이 남지 않는다.

참고 구현 (책 예제 아님)
from langgraph.types import Command

@tool
def set_user_name(name: str, runtime: ToolRuntime) -> Command:
    """사용자 이름을 상태에 저장합니다."""
    return Command(update={
        "user_name": name,    # 상태 스키마에 user_name 필드가 있어야 함
        "messages": [ToolMessage(f"이름을 {name}(으)로 저장했습니다.",
                                 tool_call_id=runtime.tool_call_id)],
    })

17장 핵심 정리

입력 조건

마지막 메시지가 tool_calls를 가진 AIMessage여야 한다. 실행 결과는 ToolMessage로 상태에 추가된다.

병렬 실행

tool_calls에 여러 개가 있으면 함께 실행한다. 서로 독립적인 작업일 때만 이득이다.

tools_condition

tool_calls가 있으면 "tools", 없으면 END. agent ↔ tools 순환 루프를 한 줄로 구성.

handle_tool_errors

True(기본값) / False / 문자열 / 함수 / 예외 튜플. 프로덕션은 함수 핸들러 권장.

ToolRuntime

LLM에 노출되지 않는 매개변수로 도구가 그래프 상태를 읽는다.
