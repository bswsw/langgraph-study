# 16. HumanRequest 패턴: 사람에게 위임하는 그래프

《LangGraph 에이전트 비법노트》 CHAPTER 16 (p.336–346)

> [!TIP]
> **◆ 책 외 보충** — 초록색 TIP 박스는 책에 없는 내용(공식 문서, 설치된 패키지 소스, 직접 실행 테스트, 해석)이다. 그 밖의 본문은 책 내용만 정리했다.

15장은 모든 도구 호출 앞에서 멈췄다. 하지만 매번 멈출 필요는 없다. 이 장은 LLM이 **"사람의 도움이 필요하다"고 판단한 순간에만** 그래프를 `human` 노드로 보내는 패턴을 다룬다. 핵심 도구는 상태에 넣는 **커스텀 플래그**와, 실제로 실행되지 않고 신호 역할만 하는 **HumanRequest 도구**다.

> [!IMPORTANT]
> **★ 동작 순서**
> 1. LLM이 `HumanRequest` 도구를 호출하면 chatbot이 상태의 `ask_human`을 `True`로 바꾼다.
> 2. 라우터가 `ask_human`을 보고 `human` 노드로 보낸다. `interrupt_before=["human"]`이라 그 직전에 멈춘다.
> 3. 전문가 역할을 맡은 사람이 답변을 작성하면, 이를 `create_response`로 `ToolMessage`로 만들어 `update_state`로 상태에 추가한다.
> 4. `stream(None, config)`로 재개 → human 노드는 플래그만 끄고 → chatbot이 전문가 답을 바탕으로 최종 답을 만든다.

## 01 · 상태 정의, HumanRequest 스키마, 챗봇 노드

LangGraph 상태는 메시지만 담는 공간이 아니다. 커스텀 필드를 추가하면 현재 실행 조건을 더 세밀하게 표현하고, 그 값으로 흐름을 제어할 수 있다. 여기서는 필드마다 업데이트 전략이 다르다는 점이 중요하다.

| 필드 | 리듀서 | 업데이트 방식 |
|---|---|---|
| `messages` | `add_messages` | 누적(append), 같은 ID는 교체 |
| `ask_human` | 없음 | 단순 덮어쓰기(overwrite) — 마지막으로 반환된 값이 남는다 |

```python
# 08-LangGraph-State-Customization.ipynb · 상태와 HumanRequest
class State(TypedDict):
    messages: Annotated[list, add_messages]
    ask_human: bool          # 사람에게 질문할지 여부

class HumanRequest(BaseModel):
    """Forward the conversation to an expert. Use when you can't assist directly or the
    user needs assistance that exceeds your authority.
    To use this function, pass the user's 'request' so that an expert can provide
    appropriate guidance.
    """
    request: str

tool = TavilySearch(max_results=3)
tools = [tool, HumanRequest]               # LLM에게는 둘 다 보여 준다
llm_with_tools = init_chat_model("claude-sonnet-4-5").bind_tools(tools)

def chatbot(state: State):
    response = llm_with_tools.invoke(state["messages"])
    ask_human = False
    if response.tool_calls and response.tool_calls[0]["name"] == HumanRequest.__name__:
        ask_human = True
    return {"messages": [response], "ask_human": ask_human}
```

`HumanRequest`는 Pydantic 모델이라 `bind_tools`에 바로 넘길 수 있다. LangChain이 모델을 도구 스키마로 자동 변환하므로 `@tool` 데코레이터가 없어도 LLM이 도구로 인식한다.

> [!CAUTION]
> **HumanRequest는 ToolNode에 넣지 않는다**
>
> `graph_builder.add_node("tools", ToolNode(tools=[tool]))`처럼 실제 도구만 넣는다. HumanRequest는 흐름을 바꾸는 신호일 뿐이라, ToolNode에 넣으면 그래프가 이를 실제로 실행하려다 오류가 난다.

## 02 · human 노드, 조건부 라우팅, 컴파일

`human` 노드는 사람의 개입이 필요할 때 실행되며, 인터럽트를 트리거하고 사람의 응답을 기다린 뒤 대화를 이어 간다. 실제 프로덕션에서는 이 패턴으로 AI가 답하기 어려운 질문이나 민감한 의사결정이 필요한 상황에서 전문가에게 대화를 자동으로 이관하는 워크플로를 만들 수 있다.

`human` 노드는 인터럽트를 트리거하는 **자리 표시자(placeholder)**다. 사람이 인터럽트 동안 상태를 업데이트하지 않으면 "No response from human."이라는 기본 `ToolMessage`를 넣어, LLM이 요청은 했지만 답을 못 받았다는 걸 알게 한다. 그리고 `ask_human`을 `False`로 되돌려 같은 노드를 다시 방문하지 않게 한다.

```python
def create_response(response: str, ai_message: AIMessage):
    return ToolMessage(content=response, tool_call_id=ai_message.tool_calls[0]["id"])

def human_node(state: State):
    new_messages = []
    if not isinstance(state["messages"][-1], ToolMessage):   # 사람 응답이 없을 때만
        new_messages.append(
            create_response("No response from human.", state["messages"][-1])
        )
    return {"messages": new_messages, "ask_human": False}     # 플래그 해제

def select_next_node(state: State):
    if state["ask_human"]:
        return "human"
    return tools_condition(state)          # "tools" 또는 END

graph_builder.add_node("human", human_node)
graph_builder.add_conditional_edges(
    "chatbot", select_next_node, {"human": "human", "tools": "tools", END: END}
)
graph_builder.add_edge("tools", "chatbot")
graph_builder.add_edge("human", "chatbot")
graph_builder.add_edge(START, "chatbot")

graph = graph_builder.compile(checkpointer=MemorySaver(), interrupt_before=["human"])
```

> [!IMPORTANT]
> **★ 왜 마지막 메시지가 ToolMessage인지 확인하나**
>
> 사람이 인터럽트 중에 `update_state`로 ToolMessage를 이미 넣었다면, human 노드가 기본 응답을 또 넣으면 안 된다. 이 방어 로직이 없으면 사람의 응답과 "No response" 메시지가 동시에 존재하는 비정상 상태가 된다.

> [!IMPORTANT]
> **★ 왜 interrupt_after가 아니라 interrupt_before인가**
>
> `interrupt_after`를 쓰면 human 노드의 "No response" 로직이 **먼저 실행된 뒤** 멈추므로 사람이 개입할 의미가 없어진다. 노드 실행 **전에** 멈춰야 전문가가 상태를 보고 응답을 넣을 시간이 생긴다.

| 경로 | 언제 |
|---|---|
| chatbot → human | HumanRequest 호출 → 전문가에게 도움 요청 (interrupt=before) |
| chatbot → tools | TavilySearch 호출 → 검색 실행 후 chatbot으로 복귀 |
| chatbot → END | 도구 호출 없음 → 바로 답변하고 종료 |

## 03–04 · 실행, 인터럽트 확인, 수동 업데이트, 재개

```python
config = {"configurable": {"thread_id": "1"}}
user_input = "이 AI 에이전트를 구축하기 위해 전문가의 도움이 필요합니다. 도움을 요청할 수 있나요?"
graph.stream({"messages": [("user", user_input)]}, config, stream_mode="values")
# AI: Tool Calls: HumanRequest(request: "AI 에이전트 구축을 위한 전문가 도움 요청...")

snapshot = graph.get_state(config)
snapshot.next                          # ('human',) → human 직전에 멈춤

ai_message = snapshot.values["messages"][-1]
human_response = (
    "전문가들이 도와드리겠습니다! 에이전트 구축을 위해 LangGraph를 확인해 보시기를 적극 추천드립니다. "
    "단순한 자율 에이전트보다 훨씬 더 안정적이고 확장성이 뛰어납니다. ..."
)
tool_message = create_response(human_response, ai_message)
graph.update_state(config, {"messages": [tool_message]})
# → {'configurable': {..., 'checkpoint_id': '1f1117e5-...'}}

graph.stream(None, config, stream_mode="values")   # human(플래그만 해제) → chatbot 최종 답
```

업데이트 직후 메시지는 사용자 메시지 · HumanRequest 도구 호출 · 전문가 ToolMessage 세 개다. `update_state`가 반환하는 `checkpoint_id`는 상태의 특정 시점을 고유하게 식별하는 값으로, 디버깅이나 복구에 쓸 수 있다. 재개하면 human 노드는 이미 ToolMessage가 있으니 메시지를 추가하지 않고 플래그만 끈다. 최종 대화는 **Human → AI(HumanRequest) → Tool(전문가 답) → AI("전문가의 답변이 도착했습니다! ...")** 순서가 된다.

> [!TIP]
> **◆ 책 외 보충 — 같은 패턴을 `interrupt()` + `Command(resume=...)`로 쓰면**
>
> 책의 방식은 정적 인터럽트로 멈춘 뒤 바깥에서 `update_state`로 ToolMessage를 직접 만들어 넣는다. 최신 LangGraph에서는 노드 안에서 `interrupt()`로 멈추고, 재개할 때 넘긴 값을 노드가 그대로 받는 방식을 많이 쓴다. tool_call_id 매칭과 "No response" 방어 로직을 노드 한 곳에 모을 수 있다.
>
> ```python
> # 참고 구현 (책 예제 아님)
> from langgraph.types import interrupt, Command
>
> def human_node(state: State):
>     ai_message = state["messages"][-1]
>     request = ai_message.tool_calls[0]["args"]["request"]
>     answer = interrupt({"request": request})      # 여기서 멈춤, 재개 시 값이 반환됨
>     return {
>         "messages": [create_response(answer or "No response from human.", ai_message)],
>         "ask_human": False,
>     }
>
> graph = graph_builder.compile(checkpointer=MemorySaver())   # interrupt_before 불필요
>
> graph.invoke({"messages": [("user", user_input)]}, config)  # → __interrupt__ 반환
> graph.invoke(Command(resume="전문가 답변 ..."), config)      # 답변을 넣고 재개
> ```
>
> **human 노드로 가는 경로는 책 코드 그대로다.** `chatbot`(HumanRequest 호출 시 `ask_human=True`), `select_next_node`(플래그가 켜져 있으면 `"human"`), `human → chatbot` 에지는 바꾸지 않고, 위 코드처럼 `human_node`와 `compile` 두 곳만 교체한다.
>
> | 호출 | 실행 흐름 |
> |---|---|
> | 1번째 `invoke` (사용자 질문) | chatbot이 HumanRequest 호출 → `ask_human=True` → select_next_node가 `"human"` 반환 → human_node 실행 중 `interrupt()`에서 멈춤 → `__interrupt__`와 함께 반환 (앱은 여기 담긴 request를 전문가에게 보여 주고 답을 받는다) |
> | 2번째 `invoke` (`Command(resume=...)`) | human_node가 **처음부터 다시** 실행 → 이번엔 `interrupt()`가 전문가 답변을 반환 → ToolMessage 생성, `ask_human=False` → chatbot이 최종 답 생성 → END |
>
> | | 책 (정적 인터럽트) | `interrupt()` 방식 |
> |---|---|---|
> | human으로 가는 라우팅 | 같음 | 같음 — chatbot이 플래그를 켜고 select_next_node가 human으로 보냄 |
> | 멈추는 곳 | human 노드 **들어가기 전** (`interrupt_before`) | human 노드 **안** `interrupt()` 줄 |
> | 답변 전달 | 바깥에서 ToolMessage를 만들어 `update_state` | 답변 텍스트만 `Command(resume=...)`로 넘김 |
> | "No response" 방어 로직 | 마지막 메시지가 ToolMessage인지 검사 | 불필요 (`answer or ...`) |
> | 재개 | `stream(None, config)` | `invoke(Command(resume=...), config)` |
>
> 주의: 재개되면 노드가 **처음부터 다시 실행**되므로, `interrupt()` 앞에 부작용(외부 API 호출 등)을 두지 않는다.
>
> **책 코드의 함정 — 병렬 도구 호출**
>
> 이 장은 15장과 달리 `parallel_tool_calls=False`를 설정하지 않았다. LLM이 한 응답에서 TavilySearch와 HumanRequest를 함께 호출하면 `tool_calls[0]`만 검사하므로 HumanRequest를 놓칠 수 있고, human 노드도 첫 번째 호출에만 ToolMessage를 붙인다. 응답이 없는 tool_call이 남으면 다음 LLM 호출에서 Anthropic/OpenAI API가 "tool_use에 대응하는 tool_result가 없다"는 오류를 낸다. 실무에서는 `parallel_tool_calls=False`를 주거나, `any(tc["name"] == "HumanRequest" for tc in response.tool_calls)`로 검사하고 모든 호출에 응답을 채워 두는 편이 안전하다.
>
> **Pydantic 독스트링 = 도구 설명**
>
> Pydantic 모델을 `bind_tools`에 넘기면 클래스 이름이 도구 이름, **독스트링이 도구 설명**, 필드가 인자 스키마가 된다. LLM은 이 설명을 보고 "언제 HumanRequest를 부를지" 판단하므로, 17장의 `@tool` 독스트링과 같은 원칙으로 용도를 명확히 써야 한다.

## 16장 핵심 정리

| 항목 | 내용 |
|---|---|
| 커스텀 상태 필드 | 리듀서 없는 bool 플래그(ask_human)로 흐름을 제어한다. 필드마다 업데이트 전략을 다르게 둘 수 있다. |
| 신호용 도구 | HumanRequest는 Pydantic 스키마만 있고 실행되지 않는다. LLM에게만 보여 주고 ToolNode에는 넣지 않는다. |
| 선택적 HITL | 모든 도구 앞이 아니라 human 노드 앞에서만 멈춘다(`interrupt_before=["human"]`). |
| 방어 로직 | human 노드는 마지막 메시지가 ToolMessage가 아닐 때만 기본 응답을 넣고, 항상 플래그를 끈다. |
