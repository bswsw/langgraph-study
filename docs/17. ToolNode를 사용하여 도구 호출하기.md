# 17. ToolNode를 사용하여 도구 호출하기

《LangGraph 에이전트 비법노트》 CHAPTER 17 (p.347–360)

> [!TIP]
> **◆ 책 외 보충** — 초록색 TIP 박스는 책에 없는 내용(공식 문서, 설치된 패키지 소스, 직접 실행 테스트, 해석)이다. 그 밖의 본문은 책 내용만 정리했다.

`ToolNode`는 메시지 목록이 든 그래프 상태를 받아, 마지막 `AIMessage`의 `tool_calls`를 읽고 해당 도구를 실행한 뒤 그래프 상태를 업데이트하는 **LangGraph의 사전 구축 컴포넌트**(LangChain Runnable 객체)다. 사전 구축 에이전트와 바로 쓸 수 있게 설계되었고, 적절한 리듀서가 있는 `messages` 키만 있으면 어떤 `StateGraph`와도 함께 쓸 수 있다. 이 장은 단일/병렬 도구 호출, LLM 연동, 에이전트 그래프 통합, 오류 처리 전략, `ToolRuntime`을 통한 상태 접근을 차례로 다룬다.

```
INPUT: state["messages"][-1] = AIMessage(tool_calls=[...])
  → ToolNode: name으로 도구 찾기 → args로 실행
  → OUTPUT: {"messages": [ToolMessage(tool_call_id=...), ...]}
```

> [!TIP]
> **◆ 책 외 보충 — 14장 BasicToolNode와의 관계**
>
> 14장에서 직접 만든 `BasicToolNode`(마지막 메시지의 tool_calls를 돌며 도구를 실행하고 ToolMessage를 만드는 클래스)의 기능을 라이브러리가 제공하는 것이 `ToolNode`라고 보면 된다. 여기에 병렬 실행, 오류 처리, 상태 주입이 더해져 있다.
>
> 출처: 이 저장소의 14장 정리 노트와 비교한 정리

## 01 · 도구 정의와 ToolNode 초기화

`@tool` 데코레이터는 함수의 **독스트링, 매개변수 이름, 타입 힌트**를 분석해 도구 스키마를 자동으로 만든다. 독스트링은 LLM이 도구를 고를 때 보는 핵심 정보라서, 무엇을 하는지·어떤 입력이 필요한지를 짧고 명확하게 써야 한다.

```python
# 10-LangGraph-ToolNode.ipynb · 도구 두 개와 ToolNode
python_repl_tool = PythonREPLTool()

@tool
def search_news(query: str) -> List[Dict[str, str]]:
    """Google 뉴스에서 키워드로 검색합니다."""
    return GoogleNews().search_by_keyword(query, k=5)

@tool
def python_code_interpreter(code: str):
    """Python 코드를 실행합니다."""
    return python_repl_tool.invoke(code)

tools = [search_news, python_code_interpreter]
tool_node = ToolNode(tools)      # 접수 창구 직원처럼 tool_calls를 보고 해당 도구로 전달
```

## 02 · ToolNode 수동 호출 — 단일·병렬

그래프 없이 도구 동작을 빠르게 확인하거나 디버깅하려면 ToolNode만 넣은 테스트 그래프를 만들어 직접 호출한다. 조건은 하나다. **메시지 목록의 마지막이 `tool_calls`를 가진 `AIMessage`여야 한다.** `tool_calls`의 각 항목은 `name`, `args`, `id`, `type`을 가진다.

```python
test_graph = StateGraph(MessagesState)
test_graph.add_node("tools", tool_node)
test_graph.add_edge(START, "tools")
test_graph.add_edge("tools", END)
test_app = test_graph.compile()

# 단일 호출
msg = AIMessage(content="", tool_calls=[
    {"name": "search_news", "args": {"query": "AI"}, "id": "tool_call_id", "type": "tool_call"},
])
test_app.invoke({"messages": [msg]})

# 병렬 호출 — tool_calls에 여러 개를 넣으면 ToolNode가 함께 실행
msg = AIMessage(content="", tool_calls=[
    {"name": "search_news", "args": {"query": "AI"}, "id": "tool_call_id_1", "type": "tool_call"},
    {"name": "python_code_interpreter", "args": {"code": "print('Hello, World!')"},
     "id": "tool_call_id_2", "type": "tool_call"},
])
test_app.invoke({"messages": [msg]})
```

> [!CAUTION]
> 마지막 메시지가 AIMessage가 아니거나 tool_calls가 비어 있으면 ToolNode는 오류를 낸다. 수동 테스트 시 형식을 정확히 맞춘다.

병렬 호출은 뉴스 검색과 코드 실행처럼 **서로의 결과에 의존하지 않는** 작업에 유리하다. 한 도구의 결과를 다른 도구의 입력으로 써야 한다면 순차 호출이 필요하다.

> [!TIP]
> **◆ 책 외 보충 — ToolNode의 "병렬"은 실제로 어떻게 돌까**
>
> 설치된 `langgraph-prebuilt` 소스를 보면, 동기 실행(`invoke`)은 스레드 풀의 `executor.map`으로, 비동기 실행(`ainvoke`)은 `asyncio.gather`로 여러 tool_call을 동시에 실행한다. 결과 ToolMessage는 tool_calls 순서대로 돌아온다. 따라서 같은 리소스(파일, 전역 변수, PythonREPL 세션 등)를 건드리는 도구들을 병렬로 부르면 경쟁 상태가 생길 수 있다.
>
> 출처: .venv/…/langgraph/prebuilt/tool_node.py (langgraph-prebuilt 1.1.0)

## 03–04 · LLM과 함께, 그리고 에이전트 그래프로

실제로는 AIMessage를 손으로 만들지 않는다. `bind_tools()`로 모델에 도구를 알려 주면 LLM이 tool_calls가 담긴 AIMessage를 만든다. 이 메시지를 그대로 ToolNode에 넘기면 된다. **LLM은 "어떤 도구를 어떤 인자로 호출할지" 결정하고, ToolNode는 실행만 맡는** 관심사의 분리(Separation of Concerns) 패턴이다.

```python
model_with_tools = init_chat_model("claude-sonnet-4-5").bind_tools(tools)

ai_message = model_with_tools.invoke("처음 5개의 소수를 출력하는 python code를 작성해줘")
ai_message.tool_calls   # [{'name': 'python_code_interpreter', 'args': {'code': '...'}, ...}]
test_app.invoke({"messages": [ai_message]})    # LLM 결정 → ToolNode 실행

def call_model(state: MessagesState):
    return {"messages": [model_with_tools.invoke(state["messages"])]}

workflow = StateGraph(MessagesState)
workflow.add_node("agent", call_model)
workflow.add_node("tools", tool_node)
workflow.add_edge(START, "agent")
workflow.add_conditional_edges("agent", tools_condition)   # tool_calls 있으면 "tools", 없으면 END
workflow.add_edge("tools", "agent")
app = workflow.compile()
```

`tools_condition`은 LLM 응답의 tool_calls 유무만 보고 분기하는 사전 구축 조건 함수라, 분기 로직을 직접 짤 필요가 없다. 테스트 결과 에이전트는 질문 성격에 따라 스스로 판단한다.

| 질문 | 실행 경로 | 결과 |
|---|---|---|
| 처음 5개의 소수를 출력하는 python code를 작성해줘 | agent → tools → agent | 코드 실행 결과 [2, 3, 5, 7, 11]과 코드 설명 |
| search google news about AI | agent → tools → agent | search_news 결과를 정리한 답변 |
| 안녕? 반가워 | agent → END | 도구 호출 없이 바로 인사 |

## 05 · 도구 오류 처리 — handle_tool_errors

ToolNode는 도구 실행 중 발생하는 오류도 자동으로 처리한다. 책에 따르면 기본적으로 `handle_tool_errors=True`가 설정되어 있어, 예외가 나면 오류 메시지를 `ToolMessage`로 바꿔 LLM에게 전달하고, LLM은 오류를 인식해 다른 방법을 시도한다. 비활성화하려면 `ToolNode(tools, handle_tool_errors=False)`로 설정한다. 오류가 처리되면 ToolMessage의 `status` 필드는 `"error"`로 설정된다.

| 설정값 | 동작 |
|---|---|
| `True` (기본값) | 모든 오류를 잡아 오류 메시지를 LLM에 전달 — ⚠️ 책 기준, 현재 버전은 아래 보충 참고 |
| `False` | 오류 처리 비활성화, 예외가 그대로 발생 |
| `"커스텀 메시지"` | 오류 시 고정 문자열을 전달 |
| `callable` | 예외 객체를 받아 메시지를 만드는 함수 사용 |
| `(ValueError, TypeError)` | 지정한 예외 타입만 처리, 나머지는 발생 |

```python
def custom_error_handler(error: Exception) -> str:
    """오류 타입에 따라 다른 메시지를 반환하는 핸들러"""
    if isinstance(error, ValueError):
        return f"입력값 오류: {error}"
    return f"예상치 못한 오류: {error}"

tool_node_callable = ToolNode(tools, handle_tool_errors=custom_error_handler)

@tool
def error_tool(input: str) -> str:
    """항상 오류를 발생시키는 테스트 도구"""
    raise ValueError(f"잘못된 입력: {input}")

error_tool_node = ToolNode(
    [error_tool],
    handle_tool_errors="도구 실행 중 오류가 발생했습니다. 다른 방법을 시도해 주세요.",
)
# → Tool Message (Name: error_tool): 도구 실행 중 오류가 발생했습니다. 다른 방법을 시도해 주세요.
```

> [!IMPORTANT]
> **★ 프로덕션 권장 — Callable 핸들러**
>
> 오류 타입별로 LLM에게 구체적인 안내를 줄 수 있어 재시도 전략을 고르기 쉽다. 예: 인증 오류엔 "API 키를 확인하세요", 타임아웃엔 "잠시 후 다시 시도하세요".

> [!TIP]
> **◆ 책 외 보충 — 현재 버전의 기본값은 `True`가 아니다**
>
> 책은 기본값을 `handle_tool_errors=True`(모든 오류를 잡음)로 설명한다. 이 프로젝트에 설치된 **langgraph 1.2.11 / langgraph-prebuilt 1.1.0**에서는 기본값이 `_default_handle_tool_errors`라는 함수이고, 동작이 다르다.
> - LLM이 **잘못된 인자**를 넘겨 생긴 `ToolInvocationError`(스키마 검증 실패) → ToolMessage로 바꿔 LLM에 전달
> - 도구 **실행 중** 생긴 예외(위 `error_tool`의 `ValueError` 등) → **그대로 다시 발생(raise)**
>
> 즉 아무 설정 없이 쓰면 책의 설명과 달리 실행 오류에서 그래프가 멈춘다. 모든 오류를 LLM에 넘기고 싶다면 `handle_tool_errors=True`를 **명시**해야 한다.
>
> **Callable 핸들러는 타입 힌트로 잡을 예외를 정한다**
>
> 핸들러 첫 매개변수의 타입 어노테이션을 보고 처리할 예외 타입을 추론한다(`_infer_handled_types`). 책 예제처럼 `error: Exception`이면 모든 예외를, `error: ValueError | TypeError`로 쓰면 그 두 타입만 잡고 나머지는 발생시킨다.
>
> 출처: .venv/…/langgraph/prebuilt/tool_node.py — ToolNode.\_\_init\_\_ docstring, \_default\_handle\_tool\_errors, \_infer\_handled\_types

## 06 · 도구에서 그래프 상태 접근하기 — ToolRuntime

대화 기록의 길이를 보거나 커스텀 상태 값을 참조하는 등, 도구가 그래프 상태를 읽어야 할 때가 있다. 도구 매개변수에 `ToolRuntime`을 선언하면 ToolNode가 실행 시점에 **자동으로 주입**한다. 이 매개변수는 **LLM에게 노출되지 않아** 도구 스키마에 영향을 주지 않는다. 사무실의 공유 화이트보드(그래프 상태)를 볼 수 있는 열쇠에 비유할 수 있다.

```python
from langchain.tools import ToolRuntime

@tool
def get_message_count(runtime: ToolRuntime) -> str:
    """현재 대화의 메시지 수를 반환합니다."""
    messages = runtime.state["messages"]
    return f"현재 대화에 {len(messages)}개의 메시지가 있습니다."

state_tool_node = ToolNode([get_message_count])

test_messages = [
    HumanMessage(content="안녕하세요"),
    AIMessage(content="", tool_calls=[
        {"name": "get_message_count", "args": {}, "id": "state_test_id", "type": "tool_call"},
    ]),
]
# → Node: tools / 현재 대화에 2개의 메시지가 있습니다.
```

> [!TIP]
> **◆ 책 외 보충 — ToolRuntime에는 state 말고도 들어 있다**
>
> | 속성 | 내용 |
> |---|---|
> | `state` | 현재 그래프 상태 |
> | `tool_call_id` | 이번 도구 호출의 ID — 도구에서 직접 ToolMessage를 만들 때 필요 |
> | `config` | 현재 실행의 `RunnableConfig` (thread_id 등) |
> | `context` | 그래프 실행 시 넘긴 런타임 컨텍스트 (예: user_id) |
> | `store` | 장기 메모리용 `BaseStore` (컴파일 시 store를 줬을 때) |
> | `stream_writer` | 도구 실행 중 커스텀 스트리밍 출력 |
>
> 이전 버전 코드에서는 같은 일을 `Annotated[dict, InjectedState]`, `Annotated[str, InjectedToolCallId]`, `InjectedStore` 어노테이션으로 했다. 지금도 쓸 수 있지만 `ToolRuntime` 하나로 모아 쓰는 쪽이 간단하다.
>
> **읽기만이 아니라 상태 쓰기도: `Command` 반환**
>
> 도구가 `Command(update={...})`를 반환하면 ToolNode가 메시지 외의 상태 필드도 갱신한다. 이때 짝이 되는 ToolMessage를 함께 넣어야 tool_call이 응답 없이 남지 않는다.
>
> ```python
> # 참고 구현 (책 예제 아님)
> from langgraph.types import Command
>
> @tool
> def set_user_name(name: str, runtime: ToolRuntime) -> Command:
>     """사용자 이름을 상태에 저장합니다."""
>     return Command(update={
>         "user_name": name,    # 상태 스키마에 user_name 필드가 있어야 함
>         "messages": [ToolMessage(f"이름을 {name}(으)로 저장했습니다.",
>                                  tool_call_id=runtime.tool_call_id)],
>     })
> ```
>

## 17장 핵심 정리

| 항목 | 내용 |
|---|---|
| 입력 조건 | 마지막 메시지가 tool_calls를 가진 AIMessage여야 한다. 실행 결과는 ToolMessage로 상태에 추가된다. |
| 병렬 실행 | tool_calls에 여러 개가 있으면 함께 실행한다. 서로 독립적인 작업일 때만 이득이다. |
| tools_condition | tool_calls가 있으면 "tools", 없으면 END. agent ↔ tools 순환 루프를 한 줄로 구성. |
| handle_tool_errors | True(기본값) / False / 문자열 / 함수 / 예외 튜플. 프로덕션은 함수 핸들러 권장. |
| ToolRuntime | LLM에 노출되지 않는 매개변수로 도구가 그래프 상태를 읽는다. |
