# 멀티 에이전트 협업 네트워크

- 여러 에이전트가 고정된 상하 관계 없이 서로 작업을 넘기며 문제를 해결하는 구조
- 감독자가 중앙에서 조율하는 대신, 각 에이전트가 자신의 판단에 따라 다음 에이전트나 도구로 흐름을 이어감

## 라우터 함수 및 그래프 생성

- 에이전트의 출력을 확인하여 다음 노드를 결정하는 역할
- 양방향 조건부 엣지를 구성하여 순환 그래프를 생성

## 에이전트가 늘어난다면?

 N개의 에이전트가 서로 아무나에게나 핸드오프할 수 있는 완전 연결(full mesh) 구조를 만들려면, 가능한 방향성 전이(transition) 개수는 최대 N × (N-1), 즉 O(N²)입니다. 이건 피할 수 없는 조합론적 사실이에요 — 엣지로 표현하든 다른 방식으로 표현하든, "누가 누구에게 넘길 수 있는가"라는 정보 자체가 O(N²)만큼 존재해야 합니다.

```python
agents = ["researcher", "writer", "reviewer"]  # N개

for agent in agents:
    others = {a: a for a in agents if a != agent}
    workflow.add_conditional_edges(
        agent,
        router,  # 라우터(혹은 에이전트 자신)가 다음 노드 이름을 반환
        {**others, END: END},
    )
```

### Full mesh가 문제가 되는 이유

- 컨텍스트 오염: 각 에이전트가 "다른 모든 동료에게 넘길 수 있다"는 걸 프롬프트/도구 목록에 다 알아야 하므로, 에이전트가 늘수록 각 에이전트의 시스템 프롬프트와 도구 목록이 선형이 아니라 사실상 전체 그래프 크기에 비례해 커짐
- 라우팅 판단 부담: LLM이 매 턴마다 "N-1명 중 누구에게 넘길까"를 판단해야 함 — 선택지가 늘수록 오판 확률·토큰 비용 증가
- 디버깅/예측 불가능성: 누가 누구를 호출할지 경로가 고정돼 있지 않으니, 무한 루프나 핑퐁(A→B→A→B...) 같은 실패 모드를 막기 위한 recursion_limit, 종료 조건 설계가 더 까다로워짐
- 실제로 필요한 관계는 훨씬 적음: researcher가 reviewer에게 직접 넘길 일이 없는데도 "이론상 가능"하게 열어두면, 있지도 않은 관계에 대한 판단 로직만 늘어남

### Full mesh가 정당화되는 경우

- 에이전트 수가 아주 적을 때(2~3개)는 O(N²)이 O(N)이나 다름없어서 문제가 안 됨 — 12장 예제가 딱 이 경우
- 정말로 "어느 순서로 누가 개입할지 예측 불가능한" 협업(자유 토론형 멀티 에이전트, 브레인스토밍 등)에서는 제약을 덜 두는 게 오히려 목적에 맞음
