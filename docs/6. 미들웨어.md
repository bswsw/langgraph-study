## 미들웨어

- 미들웨어 네가지 핵심 기능
  - 모니터링
  - 수정
  - 제어
  - 강제
- 훅
  - before_agent
  - before_model
  - after_model
  - after_agent
  - wrap_tool_call
  - wrap_model_call
- 내장 미들웨어


| 미들웨어                       | 사용 훅                          | 설명                                                                                                          |
| -------------------------- | ----------------------------- | ----------------------------------------------------------------------------------------------------------- |
| `SummarizationMiddleware`  | `before_model`                | 모델 부르기 **직전**에 메시지 목록을 확인해서, 토큰 임계값 넘으면 그 자리에서 요약본으로 교체 후 모델에 넘김                                            |
| `ModelCallLimitMiddleware` | `before_model`, `after_model` | `before_model`에서 호출 수를 세고 한도 초과 시 모델 호출 자체를 막음, `after_model`에서 카운터를 갱신                                     |
| `ToolCallLimitMiddleware`  | `after_model`                 | 모델이 응답(tool_calls 포함)을 낸 **직후**에 지금까지 도구 호출 수를 확인해서 한도 넘으면 개입                                               |
| `ModelFallbackMiddleware`  | `wrap_model_call`             | 랩 스타일이라 `handler(request)`를 직접 호출해보고 실패하면 catch해서 다른 모델로 **재호출** 가능 — 이건 before/after로는 못 하고 wrap이라야 가능한 패턴 |
| `PIIMiddleware`            | `before_model`, `after_model` | `before_model`에서 사용자 입력(요청 전) PII 검사, `after_model`에서 모델 출력(응답 후) PII 검사 — 양쪽 다 감지해야 하니 두 훅 다 사용            |
| `ToolRetryMiddleware`      | `wrap_tool_call`              | 도구 실행을 감싸서 실패 시 `handler`를 **여러 번** 재호출(지수 백오프) — 이것도 wrap이 아니면 불가능한 패턴                                     |


- 데코레이터 방식
  - 단일 훅에 가까움
  - 복잡한 설정이나 상태 초기화 과정이 필요 없음
- 클래스 방식
  - 다양한 훅을 하나의 클래스 정의로 구현할 수 있음
  - 초기화 메서드로 임계값이나 커스텀 모델 같은 설정값을 주입받아 재사용하기 좋음
  - 에이전트 상태 스키마(`state_schema`) 확장, 전용 도구(`tools`) 등록, 스트림 변환기(`transformers`) 설정 등 컴파일 타임 구성이 가능
  - 동일 훅에 대해 동기(Sync)와 비동기(Async) 구현을 모두 포함할 수 있음
- 랩 (warp) 스타일 훅
  - handler 인자로 호출 시기와 횟수를 모두 제어할 수 있음
  - e.g. 특정 횟수만큼 재시도
- 미들웨어 실행 순서
  - before_* → 순차
    1. Middleware1.before_model
    2. Middleware2.before_model
    3. (모델 호출)
  - after_* → 역순
    1. (모델 호출)
    2. Middleware2.after_model
    3. Middleware1.after_model
  - wrap_* → 중첩
    1. Middleware1이 가장 바깥
    2. 그 안을 Middleware2가 감쌈
    3. 가장 안쪽에서 handler 실행
