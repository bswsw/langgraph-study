# 15. 중간 단계의 상태 수동 업데이트하기

《LangGraph 에이전트 비법노트》 CHAPTER 15 (p.318–335)

> [!TIP]
> **◆ 책 외 보충** — 초록색 TIP 박스는 책에 없는 내용(공식 문서, 설치된 패키지 소스, 직접 실행 테스트, 해석)이다. 그 밖의 본문은 책 내용만 정리했다.

에이전트는 질문을 받아 도구 호출을 만들고, 도구 결과를 다시 LLM에 넘겨 답을 만든다. 그런데 LLM이 만든 검색 쿼리가 부적절하거나 도구가 돌려준 결과를 그대로 쓰기 어려운 경우가 있다. 이 장은 **도구 실행 직전에 그래프를 멈추고, 상태를 사람이 직접 고친 뒤 이어서 실행**하는 방법을 다룬다. 더 나아가 체크포인트에 저장된 **과거 스냅샷으로 돌아가 상태를 바꾸고 다시 실행(리플레이)**하는 방법까지 살펴본다.

> [!IMPORTANT]
> **★ 세 가지 개입 방식**
> - **도구 출력 바꾸기**: 검색을 실제로 하지 않고, 사람이 쓴 결과를 `ToolMessage`로 주입한다. (04절)
> - **도구 입력 바꾸기**: LLM이 만든 `tool_calls`의 검색 쿼리를 고친 뒤, 실제 검색이 실행되게 한다. (05–06절)
> - **과거 시점 바꾸기**: `get_state_history`로 과거 체크포인트를 골라 수정하고 그 시점부터 다시 실행한다. (07절)
>
> 세 방식 모두 **get_state로 확인 → update_state로 수정 → stream(None, ...)으로 재개** 순서로 진행한다.

```
stream(..., interrupt_before=["tools"]) → get_state(config) → update_state(config, {...}, as_node=...) → stream(None, config)
```

## 01–03 · 그래프 정의, 인터럽트 설정, 현재 상태 분석

그래프 자체는 앞 장의 에이전트(chatbot ↔ tools)와 같다. 이번 장에서 중요한 차이는 두 가지다.

- `MemorySaver` 체크포인터를 붙인다. 체크포인터가 있어야 인터럽트로 멈추고, 상태를 고치고, 다시 이어갈 수 있다.
- `bind_tools(tools, parallel_tool_calls=False)`로 도구 호출을 순차적으로 처리하게 한다.

```python
# 07-LangGraph-Manual-State-Update.ipynb · 그래프 구성 (요약)
class State(TypedDict):
    messages: Annotated[list, add_messages]

tool = TavilySearch(max_results=1)
llm = init_chat_model("claude-sonnet-4-5")
llm_with_tools = llm.bind_tools([tool], parallel_tool_calls=False)

def chatbot(state: State):
    return {"messages": [llm_with_tools.invoke(state["messages"])]}

graph_builder = StateGraph(State)
graph_builder.add_node("chatbot", chatbot)
graph_builder.add_node("tools", ToolNode(tools=[tool]))
graph_builder.add_conditional_edges("chatbot", tools_condition)
graph_builder.add_edge("tools", "chatbot")
graph_builder.add_edge(START, "chatbot")
graph_builder.add_edge("chatbot", END)

graph = graph_builder.compile(checkpointer=MemorySaver())
```

`interrupt_before`는 디버거의 **브레이크포인트**처럼 지정한 노드가 실행되기 직전에 그래프를 멈춘다. 어떤 노드에 걸 수 있는지는 `graph.channels`로 확인할 수 있다.

```python
list(graph.channels)
# ['messages', '__start__', '__pregel_tasks', 'branch:to:chatbot', 'branch:to:tools']

config = RunnableConfig(configurable={"thread_id": "1"})
events = graph.stream(
    input=State(messages=[("user", "LangGraph가 무엇인지 조사하여 알려주세요!")]),
    config=config,
    interrupt_before=["tools"],
    stream_mode="values",
)
# → AI Message: Tool Calls: tavily_web_search(query: "LangGraph란 무엇인가") 에서 멈춤
```

멈춘 상태에서 `graph.get_state(config).values["messages"][-1]`을 보면, 원래 질문 "LangGraph가 무엇인지 조사하여 알려주세요!"가 LLM에 의해 **"LangGraph란 무엇인가"**로 압축된 것을 알 수 있다. 이런 쿼리로는 원하는 검색 결과가 안 나올 수 있으니 사람이 개입할 이유가 생긴다.

> [!TIP]
> **◆ 책 외 보충 — `parallel_tool_calls=True`면 인터럽트는 어떻게 될까**
>
> 책은 `False`로 둔 이유를 "도구 호출을 순차적으로 처리"라고만 설명한다. `True`면 LLM이 한 AIMessage에 도구 호출을 여러 개 담을 수 있는데, **인터럽트 자체는 정상 동작한다.** 다만 인터럽트는 노드 단위로 걸리고 ToolNode는 여러 호출을 한 스텝에서 같이 실행하므로, **호출과 호출 사이에서는 멈출 수 없다.**
>
> | 설정 | 멈춘 횟수 | 멈춘 시점 |
> |---|---|---|
> | `interrupt_before=["tools"]` | 1번 | 두 호출 모두 실행 **전** (`next=('tools',)`) |
> | `interrupt_after=["tools"]` | 1번 | 두 호출 모두 실행 **후** (ToolMessage 2개 생성 뒤) |
>
> 문제는 멈춘 뒤 상태를 **고칠 때**다. 이 장의 수정 코드는 "호출이 항상 1개"라는 전제로 `tool_calls[0]`만 다룬다.
>
> | 멈춘 뒤 하는 일 | True여도 괜찮나 |
> |---|---|
> | 상태 확인만 하고 `stream(None)`으로 재개 | 괜찮음 |
> | 호출 목록을 보고 진행/중단만 판단 | 괜찮음 |
> | 결과 직접 주입 (04절) | 주의: ToolMessage를 하나만 넣고 `as_node="tools"`로 업데이트하면 그래프는 tools가 끝난 것으로 보고 chatbot으로 넘어간다. 나머지 호출은 결과 없이 남고, 다음 LLM 호출에서 "tool_use에 대응하는 tool_result가 없다"는 API 오류가 난다. → 모든 `tool_call_id`에 ToolMessage를 넣어야 한다. |
> | 쿼리 수정 (06·07절) | 주의: `tool_calls=[new_tool_call]`은 목록을 통째로 바꾸므로 다른 호출이 오류 없이 사라진다. → 목록을 복사해 해당 항목만 고친다. |
>
> ```python
> # 참고 구현 (책 예제 아님) · 호출이 여러 개일 때
> # 결과 주입: 모든 호출에 ToolMessage
> graph.update_state(config, {"messages": [
>     ToolMessage(content=..., tool_call_id=tc["id"]) for tc in last_message.tool_calls
> ]}, as_node="tools")
>
> # 쿼리 수정: 목록 복사 후 바꿀 항목만
> new_tool_calls = [tc.copy() for tc in existing_message.tool_calls]
> new_tool_calls[1]["args"] = {"query": "..."}
> new_message = AIMessage(content=existing_message.content,
>                         tool_calls=new_tool_calls, id=existing_message.id)
> ```
>
> 정리하면 `False`는 인터럽트가 동작하게 하려는 설정이라기보다, 멈출 때마다 호출이 1개가 되도록 고정해 **상태 수정 코드를 단순하게 유지하려는 설정**으로 볼 수 있다(해석). 책 코드를 그대로 쓴다면 `False`를 유지한다.
>
> - `parallel_tool_calls`는 **LLM이 응답 한 번에 도구 호출을 여러 개 담을 수 있는지**를 정하는 `bind_tools` 옵션이다. 같은 도구를 여러 번 부르는 것도 포함된다. 도구 실행 방식이나 사람 승인과는 무관하다.
> - `True`는 허용일 뿐 강제가 아니다. 앞 결과가 필요한 호출이면 LLM이 알아서 순차로 요청한다. `False`면 독립적인 호출이어도 응답마다 1개씩, 여러 턴에 걸쳐 자동으로 진행된다.
> - 사람의 승인을 받게 만드는 것은 `interrupt_before`다. 15장은 두 설정을 함께 써서 "멈출 때마다 확인할 호출이 1개"가 되게 한다.
>
> 출처: 직접 실행 테스트 — langgraph 1.2.11 / langgraph-prebuilt 1.1.0, 도구 호출 2개를 내는 가짜 chatbot으로 확인 (API 오류 부분은 Anthropic tool use 규칙 기준, 실행 확인 안 함)

## 04 · 사람의 개입으로 검색 결과 수정하기 (도구 출력 바꾸기)

웹 검색 결과에는 잘못된 정보가 섞일 수 있고, 이는 최종 답변 품질에 바로 영향을 준다. 그래서 실제 검색을 하지 않고 **사람이 검증한 내용을 `ToolMessage`로 직접 넣는다.**

> [!IMPORTANT]
> **★ tool_call_id는 반드시 맞춰야 한다**
>
> `tool_call_id`는 LLM이 도구 호출을 요청할 때 만든 고유 식별자다. 이 ID로 "어떤 도구 호출에 대한 응답인지"를 매칭한다. 주입하는 `ToolMessage`의 `tool_call_id`가 원래 호출과 다르면 LLM이 응답을 올바르게 처리하지 못한다.

```python
from langchain_core.messages import AIMessage, ToolMessage

last_message = graph.get_state(config).values["messages"][-1]
tool_call_id = last_message.tool_calls[0]["id"]   # toolu_01PeVf89...

new_messages = [
    ToolMessage(content=modified_search_result, tool_call_id=tool_call_id),
]

graph.update_state(
    config,
    {"messages": new_messages},   # add_messages 리듀서 → 기존 목록에 "추가"됨
    as_node="tools",              # tools 노드가 실행된 것처럼 취급
)
```

### update_state 메서드

`update_state`는 주어진 값으로 그래프 상태를 갱신하는 핵심 메서드다. **지정한 `as_node`에서 값이 나온 것처럼** 동작한다. 체크포인터로 이전 상태를 불러와 새 상태를 저장하므로 버전 관리와 지속성이 보장되고, 그래프 단계를 시뮬레이션하므로 trace도 남는다.

| 매개변수 | 의미 |
|---|---|
| `config` | 실행 구성(`RunnableConfig`)을 지정한다. |
| `values` | 업데이트할 값을 딕셔너리 형태로 전달한다. `messages`에는 `add_messages` 리듀서가 적용되어 있으므로 기존 메시지를 덮어쓰지 않고 새 메시지가 추가된다. |
| `as_node` | 값의 출처로 간주할 노드 이름. 기본값 `None`이면 마지막으로 실행된 노드가 자동 선택된다. |
| 반환값 | 업데이트된 상태를 가리키는 `RunnableConfig` (`thread_id`, `checkpoint_id` 포함) |

`as_node="tools"`로 업데이트하면 다음 노드는 tools 다음인 `chatbot`이 된다(`snapshot.next == ('chatbot',)`). 이제 `graph.stream(None, config)`처럼 **입력에 `None`**을 주면 상태에 아무것도 추가하지 않고 이어서 실행하며, chatbot은 주입된 ToolMessage를 바탕으로 최종 답을 만든다. 최종 답변 자체를 고치고 싶다면 `as_node="chatbot"`으로 `AIMessage`를 넣으면 된다.

다 끝난 뒤 스냅샷의 메시지는 `HumanMessage → AIMessage(도구 호출) → ToolMessage(수정된 결과) → AIMessage(최종 답)` 순서이고, `snapshot.next`가 빈 튜플 `()`이면 실행이 끝난 것이다.

## 05–06 · 인터럽트 후 검색 쿼리 수정하기 (도구 입력 바꾸기)

04절은 도구의 *출력*을 바꿨고, 이번에는 도구의 *입력*, 즉 LLM이 만든 쿼리를 바꾼다. 도구가 실제로 실행되므로 **검색 결과의 실시간성은 유지하면서 쿼리 품질은 사람이 보장**할 수 있다는 장점이 있다. 새 `thread_id`로 "LangGraph에 대해서 배워보고 싶습니다. 유용한 자료를 추천해 주세요!"를 실행하고 tools 직전에서 멈춘다.

> [!IMPORTANT]
> **★ add_messages는 ID로 교체/추가를 가른다**
>
> | 메시지 ID | 동작 |
> |---|---|
> | 같은 ID | 기존 메시지를 새 메시지로 **교체(Replace)** |
> | 다른 ID / ID 없음 | 리스트 끝에 새 메시지로 **추가(Append)** |
>
> 그래서 도구 호출 쿼리를 바꿀 때는 **새 AIMessage의 id를 기존 메시지 id와 같게** 둬야 한다. 그래야 메시지가 하나 더 쌓이지 않고 기존 호출이 수정된다.

```python
snapshot = graph.get_state(config)
existing_message = snapshot.values["messages"][-1]
# tool_calls[0] = {'name': 'tavily_web_search',
#                  'args': {'query': 'LangGraph 튜토리얼 학습 자료 추천'},
#                  'id': 'toolu_012nV7...', 'type': 'tool_call'}

new_tool_call = existing_message.tool_calls[0].copy()   # name/id/type 유지
new_tool_call["args"] = {"query": "LangGraph site:teddylee777.github.io"}

new_message = AIMessage(
    content=existing_message.content,
    tool_calls=[new_tool_call],
    id=existing_message.id,   # 같은 ID → 추가가 아니라 교체
)

graph.update_state(config, {"messages": [new_message]})   # as_node 생략 → 마지막 업데이트 노드
graph.stream(None, config, stream_mode="values")       # tools가 수정된 쿼리로 실제 검색
```

업데이트 후 `tool_calls`를 다시 보면 `args`의 query가 'LangGraph 튜토리얼 학습 자료 추천' 대신 'LangGraph site:teddylee777.github.io'로 바뀌어 있다. 이어서 같은 스레드에 추가 질문을 보내 전체 대화 흐름을 확인한다.

```python
events = graph.stream(
    {"messages": ("user", "내가 지금까지 배운 내용에 대해서 매우 친절하고 정성스럽게 한국어로 "
                          "답변해줘! 출처를 반드시 포함해줘!")},
    config,
    stream_mode="values",
)
for event in events:
    if "messages" in event:
        event["messages"][-1].pretty_print()

graph.get_state(config).values["messages"][-1].pretty_print()   # 수정된 쿼리 기반 최종 응답
```

`tool_calls[0]`의 속성은 `name`(도구 이름), `args`(검색 쿼리), `id`(도구 호출 ID), `type`(`tool_call`)이다. `copy()`로 복사하면 `id`가 바뀌지 않아 의도치 않게 메시지가 추가되는 문제를 막을 수 있다.

> [!TIP]
> **◆ 책 외 보충 — `dict.copy()`는 얕은 복사다**
>
> 책 예제는 `new_tool_call["args"] = {...}`로 **args 딕셔너리를 통째로 바꾸기 때문에** 안전하다. 그런데 `new_tool_call["args"]["query"] = "..."`처럼 안쪽 값을 직접 고치면, 얕은 복사라서 **원본 메시지의 args도 같이 바뀐다.** 과거 스냅샷 객체까지 오염될 수 있으니, 안쪽을 고칠 생각이면 `copy.deepcopy()`를 쓰는 편이 안전하다. 같은 이유로 `config.copy()`도 `configurable` 딕셔너리는 원본과 공유한다.
>
> **메시지 삭제는 `RemoveMessage`**
>
> `add_messages`는 교체·추가 외에 삭제도 지원한다. `update_state(config, {"messages": [RemoveMessage(id=msg.id)]})`로 특정 메시지를 지울 수 있다. 단, 도구 호출 `AIMessage`만 지우고 짝이 되는 `ToolMessage`를 남기면(또는 그 반대) 모델 API가 오류를 낼 수 있으니 짝을 같이 정리해야 한다.
>
> 출처: Python 표준 라이브러리 copy 모듈 · langgraph.graph.message.add_messages 동작

## 07 · 지난 스냅샷의 결과 수정 및 리플레이하기

**리플레이(Replay)**는 특정 과거 체크포인트로 되돌아가 상태를 고친 뒤 해당 노드부터 다시 진행하는 것이다. 영화를 특정 장면으로 되감아 다른 결말을 찍는 것과 비슷하다. 디버깅, A/B 테스트, 에이전트 의사결정을 소급해서 고쳐야 할 때 쓸모가 있다.

```python
to_replay_state = None
for state in graph.get_state_history(config):    # 상태 기록 가져오기
    messages = state.values["messages"]
    if len(messages) > 0:
        print("메시지 수:", len(messages), "다음 노드:", state.next)
        if len(messages) == 2:                     # Human + AI(도구 호출)
            to_replay_state = state
```

고른 스냅샷의 마지막 메시지는 `display_message_tree`(langchain_teddynote)로 계층 구조를 확인할 수 있다. 이후 05–06절과 같은 방식으로 쿼리를 `"LangGraph human-in-the-loop workflow site:reddit.com"`로 바꾼 새 AIMessage를 만들고, 이번에는 **과거 체크포인트의 config**를 대상으로 업데이트한다.

```python
updated_state = graph.update_state(
    to_replay_state.config,          # 현재가 아닌 과거 체크포인트를 대상으로
    {"messages": [new_message]},
)
# {'configurable': {'thread_id': 'ca8236', 'checkpoint_ns': '',
#                   'checkpoint_id': '1f114a84-...'}}

for event in graph.stream(None, updated_state, stream_mode="values"):
    ...   # tools가 수정된 쿼리로 검색 → chatbot이 새 답변 생성

for msg in graph.get_state(config).values["messages"]:   # 최종 결과 출력
    msg.pretty_print()
```

리플레이에 넘기는 config는 `update_state`가 돌려준 `updated_state`다. 결과 확인에 쓰는 `config`는 현재 스레드의 최종 상태를 가져오기 위한 초기 설정이다. 전체 메시지 이력을 보면 수정된 검색 쿼리가 반영되어, 새로운 검색 결과를 바탕으로 답변이 생성된 것을 확인할 수 있다.

> [!TIP]
> **◆ 책 외 보충 — 과거 시점 업데이트는 "덮어쓰기"가 아니라 "포크(fork)"다**
>
> 과거 체크포인트에 `update_state`를 하면 그 체크포인트가 고쳐지는 게 아니라, **그 체크포인트를 부모로 하는 새 체크포인트가 만들어진다.** 원래 실행 이력은 그대로 남고, 같은 스레드 안에 갈래가 하나 더 생기는 구조다. 그래서 같은 시점에서 여러 쿼리를 시험해 보는 A/B 비교가 가능하다.
>
> ```
> 원래 이력:  input → [Human+AI(쿼리 A)] → Tool(결과 A) → AI(답 A)
>                           │
> 포크:                     └→ AI(쿼리 B, 새 checkpoint_id) → Tool(결과 B) → AI(답 B) = 스레드의 최신 상태
> ```
>
> **config에 checkpoint_id가 있느냐 없느냐**
> - `get_state_history`는 **최신 체크포인트부터 과거 순서로** 스냅샷을 돌려준다.
> - `{"configurable": {"thread_id": ...}}`처럼 `checkpoint_id`가 **없는** config는 그 스레드의 가장 최근 체크포인트를 가리킨다. 결과 확인에 원래 `config`를 쓰면 포크된 최신 상태가 나오는 이유다.
> - `to_replay_state.config`나 `updated_state`처럼 `checkpoint_id`가 **있는** config는 그 특정 시점을 가리킨다. `update_state`가 돌려준 `checkpoint_id`는 방금 만들어진 새 체크포인트의 ID다.
>
> **수정 없이 다시 돌리기 = 순수 리플레이**
>
> 상태를 바꾸지 않고 `graph.stream(None, to_replay_state.config)`처럼 과거 체크포인트 config로 바로 실행하면, 그 체크포인트 **이전** 단계는 저장된 결과를 재사용하고 **이후** 단계만 다시 실행한다. LLM 호출은 다시 일어나므로 결과가 이전과 똑같다는 보장은 없다.
>
> **정적 인터럽트 vs 동적 `interrupt()`**
>
> 이 장에서 쓴 `interrupt_before`/`interrupt_after`는 노드 단위로 거는 **정적 인터럽트**다. LangGraph 공식 문서는 정적 인터럽트를 주로 **디버깅·단계별 점검용**으로 권장하고, 실제 HITL 워크플로에는 노드 안에서 조건부로 멈추는 `interrupt()` 함수와 `Command(resume=...)` 조합을 권장한다. (16장 보충에 예시)
>
> 출처: LangGraph 공식 문서 — Persistence(Time travel / Replay·Fork), Interrupts

## 15장 핵심 정리

| 항목 | 내용 |
|---|---|
| 체크포인터 필수 | 멈춤·수정·재개·리플레이 모두 체크포인터에 저장된 스냅샷 위에서 동작한다. |
| update_state + as_node | 지정한 노드가 그 값을 낸 것처럼 상태를 바꾼다. 다음 실행 노드도 이에 따라 정해진다. |
| stream(None, config) | 입력을 추가하지 않고 멈춘 지점 다음 노드부터 이어서 실행한다. |
| ID 규칙 | ToolMessage는 tool_call_id를 맞추고, 수정한 AIMessage는 기존 id를 유지해야 교체된다. |
| 리플레이 | get_state_history로 과거 config를 고르고, 그 config에 update_state 후 반환된 config로 stream. |
