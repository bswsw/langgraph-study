INTRO

두 챕터를 잇는 질문

5장과 6장은 사실 같은 인프라 위에 서 있다. 에이전트 루프는 모델 호출 → 도구 선택 → 종료 판단을 반복하는데, 미들웨어는 이 루프의 앞뒤에 코드를 끼워 넣는 일반적인 메커니즘이고, HITL은 그 메커니즘을 이용해 사람의 결정을 끼워 넣는 특수한 사례다. 실제로 HumanInTheLoopMiddleware는 그 자체로 하나의 미들웨어이며, after_model 후크에서 도구 호출을 가로채 interrupt()를 던진다. 이 노트는 6장의 일반 개념(후크·실행 순서)을 먼저 익히면 5장의 HITL이 "왜 그렇게 동작하는지" 더 잘 읽힌다는 전제로, 책 순서(5→6)를 유지하되 서로를 계속 참조하도록 구성했다.

CHAPTER 05

Human-in-the-Loop

파일 삭제, 이메일 발송, DB 수정처럼 되돌릴 수 없는 작업을 에이전트가 혼자 실행하게 두지 않는 메커니즘. 민감한 도구 호출 앞에서 그래프를 멈추고, 사람의 승인·수정·거부 결정을 받은 뒤에야 실행을 재개한다.

작동 흐름

01모델이 도구 호출 생성
02미들웨어가 호출 검사
03승인 필요 시 interrupt 발생
04상태 저장 · 실행 중지
05사람 결정 받아 재개

interrupt는 승인이 필요한 도구에서만 발생한다. interrupt_on에서 False로 지정한 도구(예: 읽기 전용 조회)는 검사 없이 바로 실행된다 — 감독 비용을 위험한 작업에만 쓰는 설계.

세 가지 결정 타입

모든 결정은 동일한 thread_id로 Command(resume=...)를 다시 호출해 전달한다.

APPROVE

제안된 도구 호출을 수정 없이 그대로 실행. 가장 단순한 경로.

EDIT

edited_action으로 인수를 바꿔 실행. 수신자·파일명 등 세부값 조정에 사용.

REJECT

message로 거부 사유를 피드백. 에이전트가 이를 읽고 재시도·재작성.

기본 설정 코드

HumanInTheLoopMiddleware를 create_agent에 추가하고, 도구별로 interrupt_on을 지정한다. 체크포인터는 필수 — 없으면 interrupt 이후 재개가 불가능하다.

pythonHITL 미들웨어 등록
from langchain.agents import create_agent
from langchain.agents.middleware import HumanInTheLoopMiddleware
from langgraph.checkpoint.memory import InMemorySaver

agent = create_agent(
    model=model,
    tools=[write_file, read_file, delete_file],
    middleware=[
        HumanInTheLoopMiddleware(
            interrupt_on={
                "write_file": True,   # approve/edit/reject 모두 허용
                "delete_file": True,
                "read_file": False,   # 부작용 없음 → 승인 불필요
            },
            description_prefix="Tool execution pending approval",
        ),
    ],
    checkpointer=InMemorySaver(),   # 필수: 없으면 재개 불가
)

config = {"configurable": {"thread_id": "thread_001"}}
result = agent.invoke({"messages": [...]}, config=config)

if "__interrupt__" in result:
    data = result["__interrupt__"][0].value
    # data["action_requests"]  → 대기 중인 도구 호출들
    # data["review_configs"]   → 도구별 허용 결정 타입
python재개 — 세 가지 결정
from langgraph.types import Command

# approve
agent.invoke(Command(resume={"decisions": [{"type": "approve"}]}), config=config)

# edit
agent.invoke(Command(resume={"decisions": [{
    "type": "edit",
    "edited_action": {"name": "write_file",
                       "args": {"filename": "modified.txt", "content": "..."}}
}]}), config=config)

# reject
agent.invoke(Command(resume={"decisions": [{
    "type": "reject",
    "message": "백업을 먼저 만든 뒤 삭제해 주세요."
}]}), config=config)

실전 패턴 3가지

① 위험도별 차등 승인 정책 — DB 관리 에이전트

모든 도구를 동일하게 취급하지 않는다. allowed_decisions로 도구별 결정 폭을 제한할 수 있다.

도구위험도정책
read_table없음interrupt 없음 — 바로 실행
backup_database낮음approve / edit / reject 전체 허용
execute_sql높음approve / reject만 — 수정 불가. 쿼리를 임의로 편집하는 게 더 위험하다는 판단

② 다중 작업 승인

한 번의 응답에서 여러 도구가 동시에 호출되면, decisions 배열의 순서는 action_requests의 순서와 정확히 일치해야 한다. 순서가 어긋나면 엉뚱한 작업에 결정이 적용된다.

python결정 순서 = action_requests 순서
decisions = [
    {"type": "approve"},                                   # action_requests[0] : send_email
    {"type": "edit", "edited_action": {"name": "schedule_meeting",
                                        "args": {"time": "tomorrow at 3pm", ...}}},  # [1]
]

③ 조건부 승인 — 금액 임계값 자동 판단

사람이 매번 판단하지 않고, 애플리케이션 코드가 규칙에 따라 결정을 자동 생성할 수도 있다. 이체 금액이 한도를 넘으면 자동 거부, 이하면 자동 승인하는 식.

python규칙 기반 자동 결정
if amount > 1000:
    decision = {"type": "reject",
                "message": f"${amount}는 한도를 초과합니다. 담당자 승인이 필요합니다."}
else:
    decision = {"type": "approve"}

실행 라이프사이클

HITL 미들웨어 내부에서는 after_model 후크가 다음 순서로 동작한다.

after_model 내부
  1. 모델 응답에서 도구 호출 검사
  2. 승인 필요 호출이 있으면 HITLRequest 구성
  3. interrupt() 호출 → 실행 중단, 상태 저장
  4. 사람의 HITLResponse 대기
  5. approve/edit → 호출 실행 · reject → ToolMessage 합성 후 재개

모범 사례 체크리스트

1체크포인터 필수. 개발은 InMemorySaver, 프로덕션은 AsyncPostgresSaver 등 영속 저장소.
2thread_id 일관성. 최초 호출과 재개 호출은 반드시 같은 thread_id를 공유.
3결정 순서 일치. 다중 작업일 때 decisions 순서는 action_requests 순서와 동일하게.
4edit은 최소 변경으로. 필드 하나만 바꾸는 편이 안전 — 대폭 수정은 에이전트가 접근 방식을 재평가하게 만들 수 있음.
5위험도에 맞는 정책. 위험 작업은 approve/reject만, 보통 위험은 전체 허용, 안전 작업은 interrupt 자체를 생략.
CHAPTER 06

미들웨어

에이전트 루프(모델 호출 → 도구 실행 → 종료 판단)의 각 단계 전후에 커스텀 로직을 끼워 넣는 범용 메커니즘. 5장의 HITL은 이 메커니즘으로 구현된 하나의 사례일 뿐이며, 6장은 그 메커니즘 자체를 다룬다.

미들웨어가 하는 4가지 역할

모니터링

로깅·분석·디버깅. 모델 호출 전후 메시지 수, 도구 실행 결과 기록.

수정

프롬프트·도구 선택·출력 형식 변환. 동적 프롬프트, 응답 후처리.

제어

재시도·폴백·조기 종료. 실패 시 자동 재시도하거나 대체 모델로 전환.

강제

속도 제한·가드레일·PII 감지. 호출 횟수 제한, 민감정보 마스킹.

내장 미들웨어 6종

미들웨어역할핵심 파라미터
SummarizationMiddleware토큰 임계값 초과 시 대화 자동 요약trigger=("tokens",4000), keep=("messages",20)
ModelCallLimitMiddleware모델 호출 횟수 제한(무한루프·비용 방지)thread_limit, run_limit, exit_behavior
ToolCallLimitMiddleware도구 호출 횟수 제한(전역 또는 특정 도구)tool_name, thread_limit, run_limit
ModelFallbackMiddleware기본 모델 실패 시 순차적으로 대체 모델 전환대체 모델 목록을 순서대로 전달
PIIMiddleware이메일·카드번호 등 개인정보 감지·처리strategy="redact"/"mask", detector=정규식
ToolRetryMiddleware도구 호출 실패 시 지수 백오프 재시도max_retries, backoff_factor, jitter
pythonPII 감지 조합 예시
middleware=[
    PIIMiddleware("email", strategy="redact", apply_to_input=True),
    PIIMiddleware("credit_card", strategy="mask", apply_to_input=True),
    PIIMiddleware("api_key", detector=r"sk-[a-zA-Z0-9]{32}", strategy="mask"),
]

커스텀 미들웨어 — 두 가지 작성법

데코레이터 기반클래스 기반
적합한 경우후크 하나면 충분한 간단한 로직여러 후크를 함께 쓰거나 상태를 유지해야 할 때
선언 방식@before_model, @after_model, @wrap_model_call 등AgentMiddleware 상속 후 메서드 오버라이드
예시로깅 한 줄, 동적 프롬프트 한 함수재시도 카운터, 메시지 한도 등 내부 상태를 가진 로직

노드 스타일 후크 vs 랩 스타일 후크

before_* / after_*는 정해진 시점에 한 번 실행되는 노드 스타일이고, wrap_model_call / wrap_tool_call은 handler를 직접 호출하는 랩 스타일이다. 랩 스타일은 handler를 0번(단락 처리) · 1번(정상 흐름) · 여러 번(재시도) 호출할지 스스로 결정할 수 있어 재시도·캐싱·모델 전환 같은 고급 제어에 쓰인다.

pythonwrap_model_call — 대화 길이에 따른 동적 모델 선택
class DynamicModelMiddleware(AgentMiddleware):
    def wrap_model_call(self, request, handler):
        if len(request.messages) > 10:
            new_request = request.override(model=init_chat_model("claude-sonnet-4-5"))
        else:
            new_request = request.override(model=init_chat_model("claude-haiku-4-5"))
        return handler(new_request)

실행 순서 규칙

미들웨어를 여러 개 등록했을 때, 후크 종류에 따라 순서가 다르게 적용된다.

before_* → 순차
  1. Middleware1.before_model
  2. Middleware2.before_model
  3. (모델 호출)
after_* → 역순
  1. (모델 호출)
  2. Middleware2.after_model
  3. Middleware1.after_model
wrap_* → 중첩
  1. Middleware1이 가장 바깥
  2. 그 안을 Middleware2가 감쌈
  3. 가장 안쪽에서 handler 실행

등록 순서 middleware=[M1, M2] 기준: before는 M1→M2, after는 M2→M1로 뒤집힌다. 양파처럼 감싸는 구조라고 생각하면 wrap 계열의 중첩도 같은 방식으로 이해된다.
